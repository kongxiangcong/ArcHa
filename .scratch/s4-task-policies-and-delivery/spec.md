# S4：任务策略、成果接纳与交付闭环

Status: resolved

2026-11-01：已按用户授权完成六票实施、逐项验收、审查修复及框架回归；事项均为 resolved。原有未提交修改保留，未启动正式研究考试。实施与验证记录见文末。

## Problem Statement

用户需要同一个引擎支持开发、优化和探索，但三类任务的进展不能都用数值冠军或运行结束表示。部分功能完成、可信性能改善、有效反证都可能有价值，却未必满足全部交付要求。

现有系统已有工作版本保存、冠军比较、交付检查、独立审核和失败修复入口，仍存在关键缺口：数值 target 未达到仅产生警告；整体审核 accept 会放行所有待审核需求；交付选择只固定代码提交，探索审核却读取当前主张；Expert 的未完成收尾与请求验收没有明确分开。用户因此可能无法确定被验收的到底是哪份成果、遗漏了什么，以及终验失败后应修成果还是补验收。

## Solution

复用既有契约、Run/Attempt、Worker、账本、成果引用、终验和修复入口，贯通“根据缺口选择工作 → 保存成果并分析反馈 → 选择明确交付候选 → 按契约验收 → 通过交付或针对缺口继续”。

Expert 判断下一步价值、工作起点与交付候选；Engine 负责真实执行、约束、计量与验收记录；必要独立 Reviewer 按需求判断证据覆盖。停止、进展、冠军与完成分别表达。历史验收情况从已有报告汇总，不为了展示而重复检验旧 revision。

## User Stories

1. 作为用户，我希望部分需求实现能被保留为进展，以便开发无需每轮先完成整个任务。
2. 作为 Expert，我希望从明确的未完成工作版本继续修复，以便复用已有成果。
3. 作为用户，我希望工作起点保留已知失败，以免选择继续工作被误认为认可交付。
4. 作为 Expert，我希望并行分支按后续工作目的选版，以免最新返回的分支自动成为起点。
5. 作为用户，我希望优化只在可比条件和必要约束成立时更新冠军，以便改善可信。
6. 作为用户，我希望超过约定噪声门槛的当前最优版本能够成为冠军，以便积累中间收益。
7. 作为用户，我希望未达到最终目标的冠军保持未完成，以免相对改善被当成任务成功。
8. 作为用户，我希望更快但算错的候选只能保留待修复，以免错误结果晋升冠军。
9. 作为用户，我希望同一数值交付门槛只维护一次，以免 target 与需求列表发生分歧。
10. 作为用户，我希望填写的 target 是必须达到的交付门槛，以便终验不会只警告后放行。
11. 作为用户，我希望没有数值目标的任务无需制造 target，以便开发与探索使用各自的验收要求。
12. 作为用户，我希望达到 target 后仍检查其他必需需求，以免单个指标替代完整验收。
13. 作为用户，我希望 Profile 不产生另一套验收标准，以便明确契约保持权威。
14. 作为 Expert，我希望保存无收益结果与有效反证，以便它们能够影响后续选择。
15. 作为用户，我希望探索允许有证据的否定答案完成任务，以免被迫证明原假设正确。
16. 作为用户，我希望核心解释或必要证据缺失时保持未完成，以免有价值的局部发现掩盖整体缺口。
17. 作为用户，我希望允许未决的范围沿用事先约定，以免研究遇到困难后临时降标。
18. 作为 Expert，我希望根据已有证据与下一步预期作用决定继续价值，以免被固定无收益次数控制。
19. 作为用户，我希望尚有预算时也允许有理由地停止，以免没有可行下一步仍消耗资源。
20. 作为用户，我希望未完成收尾说明缺口、理由及有依据的重开条件，以便之后可以接续。
21. 作为用户，我希望工具故障、用户停止及预算退出如实区分，以免它们被描述成研究穷尽。
22. 作为 Expert，我希望请求验收与未完成收尾分别表达，以便引擎只在适当时机启动交付工作。
23. 作为用户，我希望交付候选固定代码、成果和主张版本，以便知道终验实际检查了什么。
24. 作为用户，我希望审核和验收报告消费同一候选引用，以免当前主张变化偷偷改变交付对象。
25. 作为用户，我希望相关新反证和依据修订被处理，以免固定旧版本成为忽略新证据的理由。
26. 作为用户，我希望无关主张变化不触发全库重验，以便控制成本。
27. 作为用户，我希望独立审核只按契约需要触发，以免每轮工作都增加模型签字。
28. 作为 Reviewer，我希望一次调用能够审核多个需求并逐项关联判断与依据，以便完整表达覆盖范围。
29. 作为用户，我希望未覆盖、证据不足或未通过的必需项不能随整体 accept 放行，以免遗漏被掩盖。
30. 作为用户，我希望审核只为实际覆盖的版本和范围背书，以免新版本继承旧通过结果。
31. 作为用户，我希望模型审核不能替代契约要求的实测和复现，以免意见被当作运行证据。
32. 作为 Expert，我希望收到终验失败的具体缺口，以便选择修复、补测或补分析。
33. 作为用户，我希望评价工具或 Reviewer 调用失败后保留候选并补验收，以免重复开发。
34. 作为用户，我希望证据不足单独说明缺项，以免被直接归为代码缺陷或工具故障。
35. 作为用户，我希望已关闭 Run 的修复关联失败报告并创建修复 Run，以免改写原运行事实。
36. 作为用户，我希望修复沿用授权、累计用量与控制边界，以免每轮重新审批或绕过预算。
37. 作为用户，我希望修复后复验受影响要求，以免只检查原失败项而漏掉回归。
38. 作为用户，我希望仍适用的测量能够引用复用，以免报告措辞修改也触发重复实验。
39. 作为用户，我希望验收标准变化需要明确授权和新 revision，以免系统自动降低目标。
40. 作为用户，我希望仅标准变化时可以对适用旧成果重验，以免无必要地重新开发。
41. 作为用户，我希望验收文档末尾汇总各 revision 的已有结果及候选，以便查看历史而不重验旧版本。
42. 作为用户，我希望无验收记录显示未验收，以免新标准沿用旧通过结果。
43. 作为用户，我希望中断恢复复用可靠交接和回执，以免重复调用、测量、创建修复工作或记账。
44. 作为用户，我希望观察入口只展示已有事实和原件链接，以免维护第二套状态账。
45. 作为用户，我希望交付通过不自动修改主分支，以便成果验收与应用仍分开。
46. 作为用户，我希望先用轻量案例验证框架行为，以免正式研究被提前执行或模拟结果被当成模型能力证明。

## Implementation Decisions

### 契约与三类任务策略

- 延续 S0–S3 的冻结契约、显式 revision、Run 身份、工作交接、反馈分析及主张版本规则。Profile 提供默认行为，不授予权限，不建立第二套验收条件；首版不引入三套策略插件。辅助活动可跨类型，任务目标不随活动变化。
- objective 表达比较指标、方向及收益规则；constraints 表达候选必须满足的约束；新明确契约的 target 填入即为硬性数值交付门槛，可省略；requirements 表达其余功能、证据和审核要求，明确可选项沿用 required=false。同一 target 不复制到需求列表；target 不作为中间冠军必须达到的门槛。
- 开发按需求缺口推进；Expert 选择明确、可取回的工作版本，保留已知失败。版本选择不表示接纳或完成，并行完成顺序不替代选择判断，多分支不自动合并。
- 优化沿用可比性、正确性及约束、收益和噪声规则更新冠军；冠军只代表当前比较范围内的有效最佳版本，不宣称全局最优。无收益或失败候选及有价值证据继续保留。
- 探索按约定问题与证据覆盖判定完成，不要求原假设成立或所有主张受支持。有效反证可完成只要求判断真假/适用性的任务；要求解释机制或边界时仍须补齐。允许未知沿原契约范围，核心缺口、未处理矛盾不能仅写未知通过。
- 历史冻结契约、Run 和验收报告不批量改写或重新判定。旧 target 如仅代表期望，按既有契约修订流程明确新语义，不静默升级历史结果。

### 工作选择、收尾与交付候选

- 复用 Expert 计划、反馈分析和停止理由判断继续价值，不新增分数、固定无收益次数或逐轮策略报告。未完成收尾说明缺口、停止依据和有实际依据的重开条件，不穷举方法或编造条件。
- Expert 决策区分请求验收与未完成收尾。前者在已有交付授权下执行契约验收；后者保存结果和缺口，不仅因 Run 关闭就发起审核。用户停止、暂停、预算退出及真实阻塞沿已有控制规则处理，不以研究饱和掩盖，也不借收尾派发新的终验工作。
- 复用交付选择记录，固定所选代码提交、必要成果及主张的明确版本引用；探索不强造代码冠军。工作采用的主张引用与拟交付内容含义不同，不能直接混用。
- 审核与交付报告消费同一组候选引用，证据按需展开，不复制成果库或默认提交所有当前主张。选定引用仍携带相关反证、证据缺口和直接依据变化提示。
- 后续修订不静默替换候选、不继承旧审核；成果复用前沿 S3 处理相关依据变化，由 Expert 选择继续、调整或补证。无关变化不触发全库检查，已发生审核记录不改写。
- Engine 的控制、验收和持久化复用现有交付入口及单写入机制；CLI/Loop 的串联与 Engine 使用同一事实来源，不新增外层管理 Agent。中断后已可靠保存的决策、候选、回执和结果沿现有恢复机制接续，未知执行不能盲目重发。

### 必要验收与独立审核

- 终验针对明确候选及实际验收 revision 检查全部必需条件。target 未满足阻止完成；target_met、冠军更新、运行关闭和 Expert 的交付建议均不能单独表示完成。
- Reviewer 仅按契约需要调用，不常驻或逐轮调用；使用未参与该候选制作的新只读审核上下文，不强制不同模型。程序检查可执行条件，Reviewer 判断需求含义、证据覆盖和主张是否越界，不能替代要求的测量或复现。
- 扩展已有审核返回，使判断按需求身份关联必要依据或缺口；区分通过、不通过、证据不足及未覆盖，调用失败仍是执行失败。一次调用可覆盖多项，不拆成每需求一个 Worker；整体 accept 不能补齐遗漏的必需项。明确可选项不因缺失变为必需项，真实阻塞发现须保留原因。
- 审核意见仅覆盖实际读取的对象、版本和范围。材料截断或原件缺失导致必要依据不足时如实报告，不把总体总结当成证据。

### 终验失败、修复与复验

- 成果未满足要求：反馈 Expert 在原契约范围内选择修复；评价/审核执行未完成：保留候选，恢复通道并补做未完成验收；证据不足：指出缺项，由 Expert 判断补测、补分析或修成果。任何一类都不能标记完成、自动降标或无限重试。
- 已关闭 Run 不重开。需要修改成果时，从所选候选关联失败报告创建修复 Run，保留累计用量；仅重试审核不创建开发 Run。已授权范围内的后续处理不每轮询问用户，仍受预算、暂停/停止及真实能力约束。无可行下一步时允许未完成收尾。
- 故障分类以实际失败原因处理，不能因错误被笼统标为 evaluator 就要求修改契约；真正改变评价器或标准则走契约修订。错误提供必要上下文，不静默回退。
- 修复后检查受影响的验收项，不能只重复原失败项。执行逻辑变化须覆盖相关正确性和契约要求的性能检查；仅报告论述变化且测量对象、输入与条件未变，可引用有效测量并审核新论述。影响范围不明确则运行相关既有验收集，不建设通用影响分析系统。
- 新报告区分实际执行与引用证据；不将缓存或旧观测标为新实测，不把旧整体通过复制给新候选。保留旧失败报告与必要原件。

### 标准修订、历史汇总与观察

- 修改成果与改变标准分开；目标、验收含义等变化沿 S1 需要用户授权及新 revision，已有明确授权不重复询问。只改变验收标准且原证据仍适用时，复用旧成果重验，不为此创建执行 Run；继续执行则绑定新 revision 开 Run。执行目标、输入或评价器变化不能套用仅标准重验。
- 每次验收关联所选候选、实际验收 revision 及结果，执行 revision 沿原 Run 保留。验收文档末尾从已有记录汇总各标准 revision 的最近一次验收候选、结果和报告链接，无记录标未验收。同 revision 的详细历史仍在原报告按需查看。
- 历史汇总只读已有记录，不触发旧 revision 的测量、Reviewer 或重验，不另维护状态账。新标准未验收时不能替换 revision 字段而沿用旧通过。
- 现有报告与观察入口展示工作/候选/冠军的区别、完成依据或缺口、继续/停止原因和来源链接，默认简短，细节按需展开；不新增进度百分比或完整工作台。通过交付不自动应用成果到用户主分支。
- 在现有模块内切片替代旧行为，并清理已无用途的分支和重复测试/资产；只保留有明确历史读取或恢复职责的兼容路径。具体字段名、接口位置和存储布局由实现采用最小方案，无需再次访谈。

## Testing Decisions

- 用户已确认三类轻量案例和必要故障分支；沿已有最高层运行、交付/修复及只读观察入口验证，以受控 Worker/Reviewer 回执和轻量本地工具作为外部可控边界。复用真实账本与成果目录，不新增测试框架、测试专用状态或通用影响分析接口。
- 好测试验证可观察行为：实际选中版本、审核收到的需求/主张、结果和报告、下一步派发、调用次数与计量、失败原件及来源。避免锁定内部函数拆分、字段组织或仅镜像实现。
- 开发连续案例：A 可读正常输入但错误处理失败；从 A 修成 B；B 请求终验后发现边界缺陷，关联失败修成 C 并通过。核对未完成版本可续作、必要复验覆盖回归、旧报告及累计用量保留，不靠关闭 Run 宣称完成。
- 优化连续案例：100 ms 基线、94 ms 有效候选、target≤90 ms。测量条件可比且收益超过噪声门槛时更新冠军，终验仍不通过；无有价值下一步时未完成收尾，不多调用审核。保留无收益结果；更快但错误的版本不能晋升冠军。没有 target 时不制造数值完成条件，达到 target 也不绕过其他必需项。
- 优化案例独立修订分支：模拟用户明确授权改为≤95 ms，适用测量按新标准判定；新旧记录和候选清楚关联，历史表生成与读取不得增加旧 revision 检验次数。无验收记录、同 revision 多次验收及标准尚未重验的结果均如实展示。
- 探索连续案例：契约要求判断普遍提速并解释边界；有效反例否定原假设，缺少边界解释或审核遗漏该必需项时不得通过；补齐后对明确主张版本审核并交付。另核对允许未决与阻断核心交付的未知，未定不被填成成功。
- 探索候选选中 C/v2，Reviewer 和报告实际引用 v2；出现 v3 时旧审核不覆盖新版本，后续复用前处理相关变化；反证和缺口不因选择而丢失，无关主张变化不触发全库重验。
- 必要故障分支嵌入上述流程：审核调用失败仅补审核，评价启动失败补评价，证据不足安排所需补证；暂停、停止、预算及执行未知阻止不允许的派发。对已有结果/回执持久化后的恢复核对不重复开发、评价、修复 Run、调用或记账，复用 S1–S3 的恢复与计量夹具。
- 模块范围包含契约解析与准备、Expert/Worker 交接、Engine、冠军比较、交付/Reviewer、成果与主张查询、CLI 和只读观察。Prior art 是现有 make_project/engine_for/Sequence 夹具及工作版本续作、选定成果交付与证据复用、失败交付修复、标准确认、CLI 暂停不评价、审核回执重放与未知状态、主张版本审核和只读观察等测试。
- 每个实现切片带自身可观察验收；最后执行相关框架回归和三例贯通。既有 HTTP fixture 等待问题与 DSH 未运行验证边界如实报告，不将排除项计为通过，不借此扩大真实后端安装或验证范围。受控回复证明框架行为，不证明真实模型的研究判断正确。

## Out of Scope

- 正式四题考试、DeepStack 正式建模研究、性能研究结论或真实模型科研能力评估。
- 三套策略插件、全局最优证明、数值化所有研究价值、固定无收益停止次数、强制实验轮数。
- 常驻/逐轮 Reviewer、每需求一个审核 Worker、外层 Supervisor 或新编排服务。
- 新知识库、成果快照服务、平行状态账、每轮报告副本、全库扫描或为假设性风险增加哈希校验。
- 通用变更影响分析、S5 完整工作台、自动修改用户主分支、自动合并并行成果。
- 批量修改历史契约/报告、为生成历史表重复检验旧 revision、自动降低标准或重置累计用量。
- 新增 CLI 后端、真实 DSH 安装/登录/专用验证，或未经请求的外部研究调研项目。
