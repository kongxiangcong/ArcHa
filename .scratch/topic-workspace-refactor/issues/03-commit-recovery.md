# 03: 中断后恢复已提交成果

**What to build:** 用户重新进入中断的专题时，系统丢弃未完成输出、继续发布已经验证的成果并复用正式结果，使下一角色始终使用完整材料。

**Blocked by:** 02：通过通用命令运行真实 Worker

**Status:** resolved

依据：[父规格](../spec.md)、[现行执行协议](../../../opc/README.md)、[架构决策](../../../docs/adr/0001-topic-workspace.md)。原开发方案及文件清单通过 Git 查找。

**范围与归属：** 负责工作区提交与恢复协议、单步入口的恢复顺序和正式轮次推导。终止状态在本项用确定性输出覆盖，连续循环和预算行为由 05 完成。

- [x] Expert 在准备区域写完整状态与按需探针；成功验证后才进入待发布区域，发布前不改正式材料。
- [x] 准备阶段中断后可丢弃草稿并重新调用；进入待发布阶段后必须完成剩余发布，不重新调用 Worker、不回滚到半份备份。
- [x] 状态已发布但探针未发布、所有文件已发布但临时目录未清理等中断点，恢复均得到一致下一动作；只读查询在发布期间可以显示提交中。
- [x] 普通继续、提前完成、专题阻塞及收尾状态使用同一发布协议；终止或阻塞成果不额外发布实验探针。
- [x] Executor 仅发布成功验证的单份结果；正式结果已存在时恢复不会重复执行该实验，半写内容不得被识别为成功。
- [x] 恢复先于状态推导，所有恢复和清理持有工程锁且确认本次待处理进程已结束；跨进程停止归属处理由 04 衔接。
- [x] 只有日志或临时材料的步骤不计入完成轮次且可复用；破坏结构的手动修改报告具体错误，不静默跳过。
- [x] 通过故障注入和真实重新启动覆盖准备完成前后、进入提交前后、逐份发布前后及清理前；断言最终材料和下一动作，不仅断言内部调用。
- [x] 清理仅针对本次运行已无用途的临时材料；保留原件、日志和工程修改，不承诺外部实验恰好执行一次或掉电持久事务。


## Answer

- `TopicWorkspace.commit_expert` 在验证完整输出、保留授权预算并规范化状态头后进入提交阶段；继续、完成、阻塞与收尾共用发布协议。收尾是否调用由 05 接入，协议已覆盖。
- 单步持工程锁先恢复再推导下一动作；未验证草稿可丢弃，已验证提交逐份完成发布，已发布结果复用。只清理已无用途的 staging 与提示词，保留日志、原件和工程修改。
- `TopicEngine.step_locked` 提供持锁且恢复完成后的单次派发入口。正常 Worker 调用结束由已有受管理生命周期保证；崩溃残留进程的归属确认与恢复前拦截由 04 衔接，不以控制进程死亡推断实验结束。
- 按已确认边界使用 TDD：恢复缺失先失败，完成恢复后通过；收尾提交 API 缺失先失败，加入统一提交后通过。故障在真实子进程中注入文件系统边界，使用独立部署后的 CLI 重新启动并检查正式材料、轮数与下一动作。
- 验证：`test_topic_recovery.py` 的 23 项覆盖准备前/半写/完整准备、提交转入、状态与探针逐份发布、清理、完成/阻塞/收尾、结果发布前后及非法 Expert 输出；与 CLI、进程回归合跑原有 53 项通过，新增验证输出的 3 项随后通过。
- 保证限于进程中断恢复；外部副作用不回滚，未提交实验可能重跑，不承诺掉电持久事务。
