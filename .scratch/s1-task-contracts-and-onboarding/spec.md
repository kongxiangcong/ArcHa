# S1：任务契约、Profile 与准备流程

**Status:** resolved

## Problem Statement

用户需要把任务意图转成可执行契约，并可靠地准备、启动和恢复任务。当前实现存在按最新 revision、最新准备记录或最新 Run 选择对象的路径，可能让新草稿影响旧运行。

准备阶段修改候选、Brief 文字整理、预算累计和环境变化的处理也需要统一，避免增加审批、重复检查和中间文件。

## Solution

明确 Task、Onboard、Loop 的交接对象，让准备证据对应实际检查的候选内容，让每个 Run 固定绑定执行 revision。

准备阶段允许修改同一候选，首次绑定执行 Run 时冻结。恢复依据明确身份和必要兼容条件进行。默认仅展示运行对象、就绪状态和阻塞原因，详细证据按需展开。

## User Stories

1. 作为用户，我希望明确的工程任务无需创建地图即可准备，以便直接开始工作。
2. 作为用户，我希望“只准备”在准备完成后停止，以便控制执行范围。
3. 作为用户，我希望准备失败不会启动正式 Worker，以免在条件不足时消耗资源。
4. 作为用户，我希望准备阶段修改候选沿用编号，以免每次修补都产生新版本。
5. 作为用户，我希望准备审核不冻结候选，以便根据反馈继续完善。
6. 作为用户，我希望候选修改后仅补查受影响部分，以免重复检查。
7. 作为用户，我希望旧准备回执不能证明新内容已经就绪，以免错误放行。
8. 作为用户，我希望首次执行时冻结合同，以便知道实际执行依据。
9. 作为用户，我希望已冻结合同不被覆盖，以便解释历史结果。
10. 作为用户，我希望新草稿不影响旧 Run 恢复，以便并行处理修订和既有工作。
11. 作为用户，我希望修改错字和排版不会触发新版本或审批，以便轻量维护 Brief。
12. 作为用户，我希望实质需求变化按授权处理，以免系统擅自降低标准。
13. 作为用户，我希望暂停后恢复保持 Run ID、历史和累计用量，以便连续开展任务。
14. 作为用户，我希望查看状态不会恢复或重启任务，以便保留控制意图。
15. 作为用户，我希望多个可恢复 Run 存在时明确选择对象，以免恢复错误运行。
16. 作为用户，我希望已关闭 Run 默认展示原结果，以免意外重新执行。
17. 作为用户，我希望新 Run 明确记录起点，以免隐式继承旧成果或上下文。
18. 作为用户，我希望同语义的路径迁移和工具恢复可以修复后续接，以免不必要地重建任务。
19. 作为用户，我希望环境变化只重测受影响的数据，以便控制成本并保持测量可信。
20. 作为用户，我希望不兼容的旧记录仍可阅读，以便保留历史成果。
21. 作为用户，我希望 Profile 提供默认策略但不授予权限，以便方便配置且保持授权边界。
22. 作为用户，我希望后来修改的默认值不改变历史 Run，以便结果保持可解释。
23. 作为用户，我希望预算包含准备及所有 revision、Run 的累计用量，以免重启绕过限制。
24. 作为用户，我希望默认 token 无上限、时间额度为两小时，以便按时间控制投入。
25. 作为用户，我希望追加额度保留已用量，以便准确掌握总消耗。
26. 作为用户，我希望首先看到简明状态，再按需查看来源和检查细节，以免被内部信息淹没。
27. 作为用户，我希望复用既有记录和快照，以免产生额外中间文件及重复事实源。

## Implementation Decisions

- 保留四入口职责：Map 组织方向与依赖；Task 负责意图及 Brief；Onboard 负责契约准备；Loop 负责运行。入口不增加强制人工确认。
- 复用现有契约加载、准备、Engine、账本、快照和观察接口，不新增编排服务。
- 在当前 ArcHa 代码库内完成开发，不另建代码库或平行实现。优先修改、扩展现有模块和接口。
- 每个切片完成替换并通过相关验证后，及时删除被替代且已无调用的旧代码、配置、测试及文档说明，不把冗余清理留作无限期后续事项。确因已承诺的兼容行为需要保留的旧路径，应有明确用途和验证；不能以假设性兼容为由保留重复实现。清理实现不删除历史 revision、Run、结果或原始证据。
- 候选在准备阶段可修改；准备检查及审核不触发冻结。首次绑定执行 Run 时冻结，之后契约变化创建新 revision。
- 准备回执关联 Task、revision、检查时内容摘要及必要资源身份。保留旧记录，修改后只补查受影响部分，不保存每轮草稿文件。
- Task 入口判断 Brief 修改含义。文字整理直接处理；实质变化遵守契约与授权规则；只有歧义影响执行时询问用户。Engine 不重复判断自然语言语义。
- Run 固定引用一个执行 revision。编号最大不表示生效，不新增全局 active revision。
- 新建 Run 前检查授权、准备状态、来源、必要资源和能力，保存实际解析值及来源。
- 恢复明确定位原 Run；存在多个候选时要求指定对象。恢复保留身份、历史、成果和累计用量。
- 控制器中断后复用既有单写锁和恢复机制；已关闭 Run 不原地重开，也不自动新建 Run 绕过阻塞。
- 分别判断记录可读、执行可恢复和测量可复用。兼容的接入修复可续接；测量条件变化按影响重测；违反冻结契约时采用新 revision 和新 Run。
- 保留 JSON 执行配置和 Markdown Brief。Profile 提供有版本的默认策略；Task 显式配置和允许的本机绑定参与解析。本机绑定不能覆盖目标、验收和权限。
- 用户与项目硬限制取共同允许范围，null 不撤销已有明确上限。历史 Run 使用冻结值，不重新套用最新默认值。
- 首版预算按 Task 累计，覆盖准备和各 revision、Run。默认 token 无上限，时间额度 7200 秒；追加授权提高上限，不清除已用量。
- 未实现的能力保持未就绪。仅对实际启用的预算约束要求可靠计量，不因默认无上限的 token 缺少计量而阻塞。
- 观察接口默认展示 Task、revision、Run、就绪或阻塞原因及来源入口，细节按需展开。
- 历史记录不批量迁移。旧成果重验保留执行 revision 与验收 revision 的区别，不能作为恢复执行的捷径。

## Testing Decisions

- 主要测试边界为现有 Onboard → Engine 的准备、启动与恢复入口。复用临时项目、scripted Worker 和小型评价器，验证完整的外部行为。此边界已经用户确认。
- 测试契约选择、准备证据有效性、Run 身份与冻结、累计预算、恢复兼容性；不锁定内部调用顺序或私有方法。
- 复用已有准备计量、暂停恢复、合同变更、工具链变化和旧回执兼容测试模式。
- 关键场景包括：审核后修改候选不换编号；旧回执不能放行新内容；未就绪 r0002 不影响 r0001 恢复；冻结合同不可覆盖；Brief 文字整理不创建新 Run；关闭后不自动重启。
- 验证默认预算、跨准备和 Run 的累计、追加额度以及明确硬限制的优先关系。通过可控时间与用量夹具验证，不实际等待两小时。
- 观察接口仅补充必要的展示测试，确认摘要及按需展开的来源正确，不重复覆盖执行逻辑。
- 各 ticket 的完成验收同时检查被替代路径的调用和引用已清理，相关回归通过；仅保留有实际兼容职责的旧路径，避免新旧实现长期并存。
- 使用本地小任务贯通准备、执行、暂停、恢复和观察；不把这些测试通过视为正式四题通过。

## Out of Scope

Attempt DAG、并行工作区、完整会话恢复、证据导航重构、完成与重验机制重设计、完整工作台、正式四题考试。

不引入 YAML、通用 Profile 插件、跨任务预算池、全局 active revision、额外审核 Agent、草稿历史文件或批量历史迁移。
