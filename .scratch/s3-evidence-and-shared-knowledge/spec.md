# S3：证据、主张与共享知识

Status: ready-for-agent

需求及 Testing Decisions 中的测试边界已获用户确认（2026-10-31），规格已发布至本地事项库。本次仅完成规格发布，未启动实现或正式研究考试。

## Problem Statement

用户需要后续工作利用已产生的真实经验，并在新证据出现时修正旧判断。目前 S2 已提供工作结果保存、Run Expert 反馈分析、恢复和成果依赖，但反馈分析仍围绕单次 Attempt；共享入口不能可靠表达持续主张的身份、三态、修订及实际采用版本，也缺少按问题选择和展开材料的完整路径。

只追加摘要可能掩盖反证和待分析结果；只覆盖当前解释会改变历史引用的含义；固定截取最近历史则可能漏掉仍相关的依据。用户需要知道当前判断适用于什么、有什么反证或缺口、依据能否取回，以及这些认识是否真正影响下一步选择。

## Solution

沿用现有 Engine、Worker、SQLite 账本、本地原件和 Markdown 入口，补齐“保存结果 → 反馈分析 → 登记或修订主张 → 查询并采用 → 后续反馈”的闭环。原始观测保持不变，主张及其判断可以演进；代码采用、证据保存、主张状态和独立审核分别表达。

Expert 在已有调用中汇合新旧材料；Engine 检查并持久登记，提供授权范围内的查询与按需读取；Designer 回传观测、局部分析及实际采用引用。相关依据发生变化时，Expert 决定继续、调整或补证。整个流程不增加知识管理角色、独立服务或重复报告。

## User Stories

1. 作为用户，我希望执行观测与可修订主张分开保存，以便更新判断时仍能追溯原始事实。
2. 作为 Expert，我希望一次反馈分析可以不新增主张、更新已有主张或提出多条主张，以便只记录需要持续判断的内容。
3. 作为用户，我希望同一主张可以关联多次工作，以便证据不会被限制在单次 Attempt 内。
4. 作为用户，我希望一次工作可以影响多条主张，以便保留结果的不同用途。
5. 作为 Expert，我希望主张具有明确陈述、适用范围和三态判断，以便区分未定、有支持与被反驳。
6. 作为用户，我希望改变命题或实质适用范围时形成另一条主张，以免旧引用被悄悄改义。
7. 作为 Expert，我希望在同一主张下修订证据、状态和理由，以便保留认识变化及其原因。
8. 作为用户，我希望宽泛主张被反驳后仍可保留受支持的限定主张，以免局部有效经验丢失。
9. 作为 Expert，我希望无效或不可比测量先作为有效性疑点处理，以免把它直接认定为反证。
10. 作为用户，我希望分析过但仍无法判断的问题保持未定，以免反馈清空被误当成问题解决。
11. 作为 Worker，我希望当前解释旁明确显示尚未纳入的新结果，以免误以为它覆盖全部已存证据。
12. 作为用户，我希望中断、失败或预算退出后待处理反馈仍存在，以便恢复后继续分析。
13. 作为用户，我希望必要原件在工作区清理和代码回退后仍能取回，以便知识不随候选淘汰而消失。
14. 作为用户，我希望已有持久原件直接引用，以免维护多个副本。
15. 作为 Worker，我希望区分未展开、来源缺失和访问失败，以便判断还需要读取还是补证。
16. 作为 Expert，我希望来源缺失时仍能看到历史解释及其限制，以便决定是否将它作为研究线索。
17. 作为 Expert，我希望在任务范围、权限和预算内自主补证，以便必要恢复不增加常规人工审批。
18. 作为用户，我希望补证产生新观测并保留历史缺口，以免新结果冒充那一次历史执行。
19. 作为 Expert，我希望按已有身份、主张状态和问题文本查找材料，以便不必读取全部历史。
20. 作为 Worker，我希望筛选受支持主张时仍看到其条件、关联反证和未决提示，以免筛选产生片面认识。
21. 作为 Worker，我希望从摘要按需展开详情和原件，并知道查询及省略范围，以便自主分配阅读投入。
22. 作为 Expert，我希望发现当前 Task 的主张索引与待处理反馈，以便选择本轮所需材料。
23. 作为 Designer，我希望收到工作要求、固定输入和指定材料，并能在授权范围继续查询，以便完成局部工作。
24. 作为用户，我希望同一 Task 的后续 Run 能引用历史主张及原件，以便复用经验而不冒充新实测。
25. 作为 Expert，我希望根据当前用途判断历史证据的适用性，以便只在具体疑点出现时补查。
26. 作为用户，我希望跨 Task 读取遵循明确成果依赖和权限，以免共享变成全项目任意读取。
27. 作为 Expert，我希望在工作安排中声明采用的主张版本，以便后续能识别依据变化。
28. 作为 Designer，我希望在结果回传中补充执行时另行采用的主张版本，以便保存实际依据。
29. 作为用户，我希望读取记录与采用声明分开，以免“传入”或“读过”被当成已经采纳或理解。
30. 作为 Expert，我希望再次派发或使用成果时获知其直接引用已修订，以便先决定继续、调整或补证。
31. 作为用户，我希望在途 Call 保留原输入并在返回后分析变化，以免上下文被热替换或工作无故取消。
32. 作为用户，我希望历史决策保留实际采用版本，以便后来修订不改写过去。
33. 作为用户，我希望版本冲突时整份 Expert 决策暂不生效，以免反馈、主张和下一步工作处于互不一致的状态。
34. 作为 Expert，我希望冲突及最新材料被交回重新判断，并保留已有工作结果，以免为了修正决策重跑原工作。
35. 作为用户，我希望恢复同一已登记决策不重复修订、派发或计费，以便中断恢复保持原有语义。
36. 作为用户，我希望独立审核只覆盖实际审核的对象、版本与范围，以免主张修订自动继承通过意见。
37. 作为用户，我希望只读观察入口展示当前主张、依据、修订原因和后续选择，以便核对闭环而不触发执行。
38. 作为用户，我希望非法状态、无效身份和越权写入被拒绝并说明原因，以便共享记录可信且失败可定位。

## Implementation Decisions

- 复用 Engine、Ledger、成果登记与读取、Worker 交接、工具权限和只读观察模块。S3 扩展这些公共路径，不建立平行知识管道。现有 S2 反馈分析字段继续表达 Attempt 的分析，不将其强行扩展成每 Attempt 只能有一条主张。
- 结构化事实及关联沿用 SQLite 账本；原件保持本地原生格式；Markdown 提供可读导航与解释，不与数据库并列维护一份权威主张状态。具体表结构、函数和字段名由实现收敛，首版不为统一入口搬迁已有持久原件。
- 主张身份与修订版本分开。陈述或实质适用范围改变时另建主张，以必要引用关联；同一主张的证据、状态和理由变化形成可引用修订，保留旧版本和变更原因。纯措辞调整不要求新主张或独立修订文件，不以文本哈希判断语义相同。
- 主张仅使用 `unresolved`、`supported`、`refuted`，针对明确命题与范围。被替代以关系表达，不增加同义状态；来源可用性、反馈处理事实和独立审核保持各自语义。代码检查状态值，Expert 判断证据意义；记录成功不是主张成立。
- 主张登记至少能表达身份、所属任务、陈述与范围、当前判断、证据引用、必要反证或未决项、修订依据及原因；需要追溯时能定位旧版本和实际采用引用。沿用已有执行身份关联观测，不强制每次日志或每份结果产生主张，也不强制每条主张一个文件。
- Designer 提交观测、局部分析及执行中另行采用的主张版本；Expert 在已有调用中汇合新旧证据，提出保留、修订或新主张；Engine 按权限登记。Expert 在工作安排中声明依赖的主张版本。程序保存采用声明，不从材料传入或工具读取推断采用，不增加独立报告。
- 新结果保存后尚未分析时，入口保留当前解释并提示未纳入的新结果、必要条件、摘要和原件引用。复用 S2 待处理反馈，不新增处理状态账本；已分析仍可未定，调用成功或“已读”不能清除反馈，一次调用无需处理全部反馈。
- 同一 Expert 决策中的反馈处理确认、主张修订及下一步工作选择采用整体提交边界。修订必须指明依据版本；登记时任何一条版本冲突，整份决策均暂不生效，反馈仍待处理，保留回复和已完成结果，将冲突及最新材料交回 Expert 重新判断。不能重放旧输入冒充已考虑最新材料，也不重做原工作。
- 版本检查与决策持久登记在既有单写入、事务边界内完成，避免检查后又被旧建议覆盖。复用调用身份与已登记决策实现恢复；同一已生效决策重放不产生新修订或重复工作。已保存回复与已生效决策必须可辨。沿用现有预算、暂停和停止约束，不以补判断为由无限调用。
- 相关工作再次派发或成果再次使用时，检查已登记的直接采用引用与修订关系；依据已变则先由 Expert 判断继续、调整或补证。继续采用旧版本时记录范围与理由。未知影响不能默认仍适用，未显式登记的语义依赖不宣称已覆盖。
- 已执行中的 Call 保留实际输入，主张变化不自动取消或热替换上下文；返回后由 Expert 结合变化分析。历史成果和旧判断保留，不自动把下游主张改为被反驳，不推导全局知识依赖图。
- 查询能力复用成果访问入口，支持按已有身份、三态和问题文本筛选，首版采用简单筛选和文本查找。返回主张时同时携带适用条件、已登记关键反证、未决或缺项提示及来源入口；按 `supported` 筛选不能裁掉关联反证。查询范围、未展开正文和省略须可辨，提供后续详情及原件读取路径，不依赖固定历史窗口。
- Expert 初始入口覆盖本 Task 的主张索引与待处理反馈；Designer 初始材料围绕本次工作、固定输入和 Expert 指定依据组织。Worker 可在角色授权内继续查询，不强制固定阅读顺序、数量或每次必调工具。提示词只补材料入口、查询方法、覆盖范围和必要输出约定。
- 同一 Task 的后续 Run 可按权限查询历史主张和原件，并引用实际采用版本。跨 Task 限明确成果依赖及权限；共享可读不授予任意覆盖权限。历史记录可读不等于测量可复用，Expert 根据当前用途判断条件变化，不因更换 Run 无条件重测。
- ArcHa 自身产生、被主张引用且仅存在临时工作区的必要原件须在清理前进入既有持久成果位置。已可靠保存的原件直接引用；代码回退不删除必要证据。保留必要 trace，不镜像整个工作区，不新增自动清理或全量哈希扫描。
- 来源缺失或读取失败时保留历史引用及判断并显示具体缺口，不自动改为 `refuted`，不默默改指新结果。登记、实际读取和必要交付检查只核对相关来源，不逐轮扫描全库。
- Expert 在既有任务、权限和预算内按用途自主补证；历史解释可以带限制作为线索，必须核对原件的判断或验收在缺口补齐前不能宣称完成。新测量保留为新观测，当前依据更新关联旧引用及补证原因；如契约要求核对那一次历史执行，重新测量不能替代。其他独立工作可继续。
- 外部资料可正常引用，失链时重新调研并更新当前依据；不管理其归档或版本，不将文献叙述冒充本次测量。此边界不改变 ArcHa 自身必要结果及调用记录的保存要求。
- 审核仅在实际发生时关联对象、版本及范围，修订不继承旧审核通过意见，也不将旧审核改写成失败。S3 不新增中途审核触发点，具体策略交 S4；日常反馈由 Expert 完成。
- 只读观察出口复用同一事实来源，展示主张、证据、历史修订、未处理反馈及有关工作选择；不建立 UI 专用权威状态。代码能证明交付和登记内容、可观察的读取行为，不能证明模型理解正确或穷尽反证。

## Testing Decisions

以下测试边界已获用户确认（2026-10-31）；验收行为来自已确认需求。

- **主测试边界：Engine 的运行、恢复与 Worker 交接。** 沿用临时项目、真实账本与成果目录、脚本化 Worker 的集成夹具，驱动完整流程；观察实际送达上下文、查询结果、主张历史、后续选择和原件可取回性。测试不绑定私有方法调用顺序、内部表布局或提示词整段快照。
- **必要补充：已有成果读取与只读观察出口。** 用公开查询/读取契约验证筛选、展开、省略、缺失与授权范围；观察出口只核对同一事实的投影及只读性。主张存储和关联以集成流程覆盖，默认不再创建独立仓储测试接口。
- 主线案例使用约定范围内“减少复制总能提速”的主张 A：初始未定；长字段有效测量支持另一个限定主张 B；短字段退化保存后显示待分析；Expert 确认反例有效且属于 A 的范围后将 A 修订为被反驳，B 保持有支持；下一项工作查询并明确采用对应版本，实际选择反映范围差异。原件、旧判断及原实际交接保持可追溯。该案例是受控夹具，不宣称真实优化效果。
- 有效性分支只检验关键区别：受干扰的短字段测量不能直接反驳 A；相互不一致且尚无法解释的可比观测可以分析完成但判断未定。不要将每个可能的科研情境扩展为完整实验。
- 恢复分支覆盖结果已存但未分析时中断，恢复后入口仍提示待处理；反馈分析生效后提示与判断同步更新。覆盖已登记决策在工作创建前后中断，恢复不重复修订、调用或派发。
- 冲突案例让一份 Expert 回复中的一条修订基于过时版本，同时包含另一条合法修订、反馈分析和工作选择；确认它们全部未生效、反馈仍待处理、回复与原结果仍在，Expert 收到冲突及最新材料后才重新决策。检查原工作没有重跑。
- 查询和引用覆盖按身份、状态、文本定位，`supported` 结果保留关联反证，缺项及未展开状态可辨；确认只读取未声明采用的材料不会形成采用引用，Designer 的新增采用引用能够回传；越权写入、非法状态和无效身份被拒绝。
- 修订影响覆盖已计划工作引用旧版本时先交 Expert 判断，以及在途工作不被取消且返回后结合变化分析；确认历史交接不会被改写。同 Task 跨 Run 可查询旧主张，跨 Task 未授权材料不可读。
- 原件分支覆盖工作区清理或代码回退后必要原件仍可取回；缺失来源显式暴露，补证形成新观测并保留旧缺口。复用既有实际审核案例检查旧审核不覆盖新版本；无需为无审核的修订制造审核调用。
- Prior art：研究循环测试的 `Sequence`、`use_sequence` 及 `make_project` / `engine_for` 夹具已能采集实际上下文并驱动恢复；成果测试已有跨 Run 原件保留、登记失败后重试和审核消费版本案例；DAG 测试已有已登记批次在重启后只物化一次的案例；工具边界与观察测试已有授权读取和只读性检查。相关模块分别是 Engine、成果读取、Worker 交接、Ledger、工具权限及观察出口。
- 先运行受修改影响的现有测试及上述最小新增案例，再按实际影响执行框架回归，复用 S2 已有恢复、并行与隔离证据。必要时以一个真实轻量 Worker 案例观察查询及交接是否可用；脚本化夹具不能证明模型理解正确。真实案例应明确后端、条件、产物和限制，不据此声称正式研究验收通过。

## Out of Scope

- 知识图谱、全局依赖传播、向量服务、自动相关性评分、Memory Agent 或其他新增总结角色。
- 强制 E0–E3、数值置信度、独立审核每轮调用、新增中途审核触发点及 S4 的策略和最终交付规则。
- 外部材料归档、版本或读取时间管理、独立档案服务、远端共享存储、多控制器协调和容灾备份。
- 每条主张一个文件、每个工具结果一个主张、重复 JSON 与 SQLite 权威状态、工作区镜像、语义去重哈希及逐轮全库扫描。
- 自动垃圾回收、自动把经验提升为跨任务通用技能、自动取消依赖旧主张的在途工作。
- 通用阅读纪律、固定历史条数作为知识入口、固定阅读层数或每轮强制查询次数。
- 新建观察 UI、重做 S1/S2、为术语统一强制改名现有反馈字段、未触及功能的测试重构。
