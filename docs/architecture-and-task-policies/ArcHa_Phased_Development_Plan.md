## 1. 开发流程与阶段合理性复核

**判断：七个方向及其依赖关系合理，没有阻塞目录生成的问题。** 本轮保留整体顺序，明确阶段与 ticket 的层级，并将最终验证收敛到 DeepStack。

| 依据 | 推导 | 规划决定 |
| --- | --- | --- |
| 用户确认阶段是大方向，阶段内还要讨论流程、接口与约束 | 当前应划定责任与依赖，不能直接把方向当成实现票 | 阶段目录承载讨论与需求；纵向切片是后续 tickets 的拆分原则 |
| 整体文档保留三类任务策略与同一个执行底座 | DeepStack 是最终应用目标，不能把框架改成只支持探索 | 三类策略保留轻量行为回归；按 S0 收束为三个模块题与一个独立端到端课题 |
| 用户明确改造完成后才跑 DeepStack 测试 | 开发反馈与最终研究验证需要不同证据来源 | S0 设计方法，S1–S5 用回归/夹具/小案例反馈，S6 才实际探索 |
| 现有实现已有账本、成果入口、无补丁测量和只读观察器 | 无需按完全缺失重建所有模块 | 各阶段先确认缺口并复用已有能力，观察出口随能力同步交付 |
| 输入契约、执行交接、证据反馈、策略判断和调试消费存在依赖 | 后续模块需要消费前面明确的事实与责任 | 保持 S1 → S2 → S3 → S4 → S5 的默认收束顺序，允许局部往返 |

需要检验的前提是“前期不跑 DeepStack，便只能等到最后获得反馈”。框架行为仍可通过已有回归、合成系统和小型案例检验，最终研究效果则由 S6 的真实任务判断。因此无需提前启动 DeepStack，也不能拿夹具成功替代真实探索成功。

另一个可选出发点是按 DeepStack 的具体部件组织全部开发阶段。它便于对齐一个项目，却容易把特定目标的知识和流程硬编码进 Harness。我们保留通用能力方向，让 DeepStack 的研究需求推动接口讨论；具体建模机制与实验路线不预写进引擎。

效率问题也可能来自上下文交接、工具延迟或证据难以读取，不一定需要大规模引擎重构。前期建立框架行为基线，后续逐项比较；局部改动已解决问题时就缩小重构。DeepStack 上的效率收益只能在正式测试后判断，不能预先承诺最优。

## 2. 每阶段怎样推进与防止偏离

阶段推进循环：

`阶段方向 → 讨论与 grill-with-docs → 用户确认需求 → to-spec → to-tickets → implement-spec → 集成验收与观察 → 阶段 review 与反馈 → 后续阶段`

阶段描述不限制为一张 ticket 的粒度。需求讨论可以发现阶段内的多个子问题；有必要时分批形成 spec，再按依赖实施。S0 是共同设计与测试方法准备，不为纯设计材料制造空的实现工单。S6 是最终研究验证方向，其探索过程由已完成的 ArcHa 执行。

讨论与 `grill-with-docs` 收敛同一份需求；spec 将需求转成行为、接口和验收约定；tickets 才拆成可以独立验证的端到端实现。实施中的测试和 code-review 可由 `implement-spec` 承担，不重复运行同一轮审核。

每个实现阶段完成需要：需求对应行为成立；外部能够观察行为与失败原因；相关已有能力无已知回归；实际结果和限制已回写。S0 的完成依据是共同边界与测试方法明确；S6 的完成依据是正式探索的证据与验收。代码 review、工单关闭、框架可运行和理解 DeepStack 分别表示不同事实。

### 范围与变更规则

- 每份阶段需求注明整体文档的相关章节、本阶段目标、In/Out、依赖和未决问题。目录建立不表示其中的配置或接口细节已经获批。
- 需求关联 spec、ticket 和验证证据，复用编号与链接，不另建追踪数据库。同一决定保留一个权威定义，其余引用。
- 字段细化与内部实现可在确认边界内决定；用途、权限、验收语义、职责或跨阶段接口发生实质变化时，返回对应讨论并记录影响。
- 整体文档允许经讨论优化。新决定注明替代的建议，不能由 ticket 静默扩大范围，也不能让旧示例阻止合理修订。
- 下一阶段先读取上一阶段的实际交付与限制，允许重排、合并或缩小后续工作，不一次冻结全部 spec 和 tickets。
- S1–S5 的反馈来自当前开发与验证；DeepStack 正式测试若暴露问题，再回到相关阶段修复，保留失败证据与原验收标准。

### 何时构成阻塞

成功标准互相矛盾、关键输入缺少可信来源、必要接口责任未定，或实施必须突破授权边界时，暂停受影响工作并讨论。尚未决定 JSON/YAML、未来插件形态或后续字段，不阻塞方向规划；进入依赖这些决定的实现前再收敛。

实际使用 Matt Pocock 流程前，要确认技能版本和工单位置。已读本地四个技能文件，首次规划未发现 `docs/agents/issue-tracker.md`；这是执行准备项。工单只选一个权威入口，阶段目录引用它，不同时维护本地与外部两套状态。本次不生成 tickets 或安装技能。

## 4. DeepStack 测试方法前置，正式执行后置

前期需要设计的是“怎样判断研究有依据、怎样观察 ArcHa”，而不是替 Agent 预先研究出 DeepStack 的答案。下表保留方法依据；当前边界已由 S0 收束，题目具体口径以各 TASK.md 为准。

| 需要确定的内容 | 方法方向 | 防止的误判 |
| --- | --- | --- |
| 研究对象与范围 | 固定 DeepStack 版本，选择需要解释的建模链路与层级；明确源码、文档、接口和运行观测的可见范围 | 把模型行为当作硬件真值；混淆整体覆盖与所有变体穷举 |
| “怎样建模”的交付含义 | 围绕实际范围说明输入与参数含义、建模分解、计算/组合关系、关键近似、输出形成方式及边界；每项结论关联依据 | 只列函数名、复述 README，或把成功运行示例当成理解完成 |
| 自主研究与证据 | Agent 自主选问题、案例、对照和观测点；规定必要记录与主张依据，不预置解法、全部探针矩阵或强制假设数量 | 测到的是照单执行能力，或结论只来自作者自述 |
| 关键结论的核对 | 区分源码/文档明确事实、实测现象和推断；按主张选独立参照、受控变化或未参与解释形成的案例；记录适用条件和反例 | 同一解释生成答案又验证自己；把重复调试案例当独立验证 |
| 完成与未完成 | 确定用途相关的研究覆盖和证据要求；未知处标明缺口。是否允许有边界的未决交付由需求讨论确认 | 预算用尽、问题数量多、文档长或没有新想法就宣布完成 |
| Harness 反馈 | 观察交接、计划与实际偏差、原件保留、知识更新、下一步是否使用新证据，以及必要资源消耗 | 框架留档完整就被当成研究结论正确；只凭总耗时归因效率 |

“理解它怎样建模”不天然要求严格黑盒。源码辅助分析与受限接口辨识各有用途，S0 根据目标选择信息边界；不额外制造隐藏答案任务。读不到或无法核对的部分保留未知，不由外部行为唯一推断内部实现。

| 时点 | 本次允许推进的测试工作 | 正式 DeepStack 探索 |
| --- | --- | --- |
| S0 | 确定测试范围/验收并封装原始材料、搭建环境、运行材料自检 | 不执行 |
| S1–S5 | 对新增框架行为做必要回归、夹具和小案例验证；随接口变化完善测试方法 | 不执行 |
| S0–S5 必要工作完成后 | 核对实际环境与版本，落实执行合同，再由 ArcHa 开展 S6 探索与结论核验 | 在 S6 执行 |

四题为 S6 必做验证；改造前后 DeepStack 全面对照以及直接 Agent 对照不作为默认必做项。若后续需要宣称跨任务泛化或 Harness 效率优势，再设计相应比较。一个 DeepStack 任务能够验证该范围内的研究能力，不足以证明全局最优或普遍优势。

当前 [四题入口](../../benchmarks/README.md) 提供独立题面与环境；具体合同由正式 ArcHa 流程产生，不预填。环境自检与正式考试分开记录。

## 5. 所有阶段共同遵守的开发规范

这些是本次需求明确提出的约束，后续需求与实现 review 都应检查，不只是原则性口号。

| 约束 | 落地判断 |
| --- | --- |
| 不过度防御、不做冗余检验 | 在真实输入/权限/持久化边界检查必要不变量；内部使用已成立的契约，不在每层重复验证同一事实。新增检查应能说明防止哪个实际失败。必要独立验收不属于冗余自检。 |
| 不做冗余哈希计算 | 不为导航、展示或每次读取遍历重算全量摘要。先利用已有稳定身份与版本；确实需要判定评价资源、审核对象或可变外部材料是否相同时，再明确最小范围和触发时机。不能用哈希替代原件存储，也不能未经分析删除现有正确性边界。 |
| 不生成冗余中间产物 | 原件保存一次，其余引用；投影按需生成。每种新增文件必须有实际消费者、权威归属或恢复用途；不制造空回执、重复摘要和给 UI 专用的状态文档。 |
| 模块化且不增加流程复杂度 | 按契约、运行、证据/知识、领域验证、观察等职责形成清楚接口，优先现有接缝；新增模块需有内聚责任，不因图里有方框就建服务。正常路径不为格式转换/总结增加 Worker 往返。 |
| 尊重模型能力 | 约束用途、权限、证据和交付；实现定位、方法选择、诊断与实验设计交给 Worker。不预写全部路线，不要求普通开发伪造假设或数值评分。 |
| 渐进式披露 | 默认相关摘要与来源，按需展开；保留条件、反证、缺失提示。实际上下文可追溯，摘要不能悄悄丢掉会改变结论的限制。 |
| 实验数据与结论规范管理 | 计划、实际执行、输入/目标/评价条件、原件、解释和审核能关联；新测量与缓存区分。无效测量不是反证；负结果与未知保留真实状态，旧审核不覆盖新结论。 |
| 有反馈但不重复劳动 | 每阶段有行为验收和可观察证据；测试围绕外部行为与有意义的失败路径。已有证据仍适用时复用，变更影响其有效性时才补测。 |
| 观察能力保持轻量 | 不引入第二份手工状态，不因查看页面额外调用模型、运行实验或扫描全部历史。读取接口与有副作用的操作分清责任。 |
| 效率结论有条件 | 不凭空设置预算或性能目标；质量与边界先成立，再用可比较记录判断改善，报告成本转移和退化。 |

减法决定：删除“三套引擎、通用工作流 DSL、重复状态系统”的方向；推迟通用策略插件、向量知识服务、团队自演化和跨任务自动技能推广，直到真实案例证明现有职责无法表达需求；将调试工具缩成贯通证据链的必要能力，扩展控制功能前先有具体使用场景。最终验证采用 S0 四题；泛化与效率对照仅在需要相应结论时安排。七个方向分别承担边界、入口、执行、反馈、判断、诊断和实证，当前都有保留理由。
