# S5 外层调试工作台整合

状态：首版范围已由 S0 确定，实现细节待设计；本阶段可以在讨论后形成多份 spec 与多张 tickets。

入口：[总规划](../ArcHa_Phased_Development_Plan.md)。整体文档依据：[§5](../ArcHa_Overall_Architecture_and_Task_Policies.md#s05)、[§10](../ArcHa_Overall_Architecture_and_Task_Policies.md#s10)、[§14](../ArcHa_Overall_Architecture_and_Task_Policies.md#s14)、[§17](../ArcHa_Overall_Architecture_and_Task_Policies.md#s17)。

**依赖：** S2–S4 的运行与观察接口；观察需求和最小界面此前已随阶段交付。

## 需要讨论的方向

- 复用现有 `opc/observer`、`/api/observer/v1` 和 `web`，完成任务/流程/Worker 状态、调用轨迹、实际上下文、证据、结论历史、共享空间和交付差异的贯通导航。
- 由运行端暴露必要事实和关系；观察适配器负责读取与展示，不依赖猜测文件标题或 Worker 为 UI 另写长报告。界面不形成新的运行状态或结论权威。
- 支持少量高价值诊断任务：定位停滞节点、检查一次错误交接、追溯结论改变、解释候选未获接纳、找到恢复所需材料。摘要先行，按需下钻，显示缺失、未知、滞后与来源。
- 只读观察是当前已有基础。首版增加暂停、继续、停止，由既有 Engine 执行并留痕；知识编辑、手工修改 DAG 和页面发起任意实验后置；界面不直接改账本、不伪造成功、不通过页面访问隐式重跑实验。完整控制台不是默认扩张项。
- 检查观察开销、分页/按需读取与源数据兼容；观察故障不应把已经成功的工作改判为失败，必需事实记录失败则按运行契约处理。

## 拟议结束条件

使用当前协议的真实记录或明确标注的夹具，能从一个异常找到对应调用、输入上下文、证据和当前判断；浏览不会执行工作或改写原件。暂停/继续/停止须验证控制留痕与恢复行为。

**本阶段不做：** 第二套业务引擎、独立知识管理数据库、大屏统计堆叠或全面重做已有 UI。

## 优先收敛的问题

1. 首先需要支持哪些具体诊断路径，已有工作台还缺哪些关键关联？
2. 怎样把已确定的观察与暂停/继续/停止接入既有引擎，并验证恢复行为？
3. 展示如何复用运行事实并按需下钻，怎样避免重复存储、全量扫描和观察开销膨胀？

本阶段使用必要的框架回归、夹具或轻量案例获得反馈；DeepStack 正式建模探索留到 S6。方法变化回写总规划中的测试方法约定，不在此提前运行研究。
