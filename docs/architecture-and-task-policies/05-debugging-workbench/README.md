## 1. 目标与信息边界

让用户在同一工作现场看清：**工作做到哪里、Worker 正在做什么、哪里需要处理，以及暂停/继续/停止是否实际生效。** 观察/API、Engine 控制和前端体验一起交付；不能只做视觉外壳，也不能把底层记录全部陈列给用户。

| 界面保留 | 内容边界 |
| --- | --- |
| 工作状态 | 工作目标、实际阶段、依赖/资源等待、阻塞原因、结果及下一步 |
| Worker 活动 | 谁处理哪项工作、读哪个文件、执行什么命令、最近结果和可确认的时间 |
| 关键材料 | 必要工作指令、交接输入输出、相关任务文件、代码、产出和有助处理失败的错误片段，按需展开 |
| 运行控制 | 暂停/继续/停止、请求反馈、实际状态、可读失败原因和可执行的下一步 |

**禁止显示任何证据和审计信息、哈希值及用户不关心的内部检验材料。** 不提供证据清单/链、主张版本溯源、审核逐项记录、原始账本/回执/事件包、来源元数据、内部校验报告或技术标识展示。侧栏、弹窗、工具提示和“高级详情”同样遵守，不用默认折叠替代移除，也不另建开发者控制台。

用户执行测试代码的命令、失败输出属于任务内容；系统内部合同完整性、日志归属等检验材料不属于任务内容。可显示“还未完成：错误输入处理失败”，无需展示内部审核过程。内部身份仍供导航和请求关联使用，必要后端记录仍按原契约保存，不因界面精简删除。

## 2. 工作与 Worker 的关系

中央以所选运行中的工作为中心；同屏紧凑 Worker 活动区是另一主要关注点。选择任一侧定位关联对象，共用按需详情。工作阶段、一次调用和一次工具动作不是同一状态：Designer 已返回，工作可能仍待评价；工具命令失败，Worker 可能继续修复；调用成功也不代表工作完成或交付通过。

同一工作可能经历多个角色及重试调用，同一角色可能并行处理多项工作。展示不能用一个“Designer 忙碌”覆盖全部调用；Run 级 Expert 决策留在运行层，不强行归属某项工作。后端会话不等于存活进程，没有在途调用仅表示当前无调用，不推断 Agent 离线或休眠。

具体活动依据真实事件：

| 可观察事实 | 界面表达示意 |
| --- | --- |
| 工具动作开始，尚无结果 | “已开始读取 parser.py”或“已启动 pytest”；只有可靠执行事实才标正在执行，不能把缺少结束记录当作持续存活证明 |
| 动作已返回 | “最近完成：读取 parser.py”或“pytest 失败，退出码 1” |
| 没有后续活动 | 保留最近动作，必要时提示暂无后续活动，不猜测思考、排队或卡死 |
| 刷新失败/执行未确认 | 保留最后已知内容，简短提示状态暂不可确认，不把观察失败改判为工作失败 |

一个调用内有多个未结束动作时保留可展开的活动列表，不因最新摘要覆盖其他动作。后端无事件时间则只显示顺序，或明确使用观察时间；不将页面刷新/文件修改时间冒充动作发生时间。只有 shell 命令时按命令展示，不分析任意脚本猜它在读取什么。没有事件支持的后端明确活动不可用，不要求 Worker 为界面另写报告。

## 3. 两条核心场景与控制语义

### A. 发现阻塞并返回现场

发现工作阻塞 → 选择工作 → 查看关联 Worker 错误及必要交接输入 → 打开相关任务文件或产出 → 返回原工作。

工作选择、筛选、局部阅读位置和焦点保留；重试调用能区分，查看的是所选那次实际交接，不能拿最新文件替代旧输入。这里只打开用户任务材料，不提供证据/审计原件入口。完整内部上下文包、原始工具事件及 JSON 不是阅读页面；任务内容须以清楚的文字和必要片段呈现，不能夸称知道模型全部上下文。

### B. 暂停后继续同一运行

暂停沿 S2 既有契约：**收住当前 Worker/评价调用，在下一次派发边界停止推进。** 一次 Worker 调用内仍可继续读文件、运行命令及模型交互；暂停不是工具级断点或进程冻结，等待期间实际执行仍计入用量。

| 操作/时点 | 顶部反馈 | 工作与 Worker |
| --- | --- | --- |
| 提交暂停 | 正在提交暂停请求 | 保留真实状态 |
| 请求已收到，未实际暂停 | 暂停请求已收到，等待生效 | 在途调用继续更新动作，不派生假完成或暂停百分比 |
| Engine 确认 paused | 已暂停；必要时提示尚未确认的执行 | 保留工作实际阶段和最后动作，例如待评价；不显示 Agent 被冻结 |
| 点击继续 | 正在提交 → 正在恢复 | 保留同一运行、所选工作、打开的文件与位置；不重新选配置或重复确认 |
| 恢复已生效 | 运行中，或直接显示已完成/实际阻塞 | 接续尚未完成的阶段；复用已有成功结果，只展示真实新活动 |
| 启动/恢复/收尾失败 | 无法继续/无法确认暂停及简明原因 | 保留原现场和已完成内容，按真实原因给有意义的下一步 |
| 网络超时或观察断开 | 暂时无法确认当前状态 | 查询实际状态，不直接认定未执行，不自动重复启动 |

暂停待生效期间避免重复提交，继续在实际暂停且符合恢复条件后可用；首版不增加撤销暂停模式。继续不自动创建新运行、切换后端、重置额度或重做已有成功调用。没有活动时不虚构 Worker 动作，不重播历史动画。恢复后立即完成或阻塞，不强制经过运行中画面。

**停止同属首版范围：** 复用 Engine 取消执行的契约，区分请求已收到与实际结束；终态未知明确提示。停止后的 closed 不代表交付成功，继续不暗中变成重新开始。不以暂停等待过久自动升级停止。沿已确认原型，停止位于顶部控制区，单独确认后提交；不扩展新的执行语义。

## 4. 空间、主题与动效（原型确认后的设计基线）

用户已确认当前原型，采用以下布局，不再并列推进多套视觉方案：

| 区域 | 已收敛的布局决定 |
| --- | --- |
| 顶部 | 任务/运行定位、实际运行状态与暂停/继续/停止；桌面详情展开不遮挡运行控制 |
| 左侧 | 默认紧凑导航，可展开文字；不占用主要工作空间 |
| 主区 | 工作列表/紧凑时间线占主要宽度；状态、等待关系和阻塞原因跟随工作呈现，保留全部/需关注筛选 |
| Worker 区 | 桌面右侧同屏紧凑活动列表，以角色、关联工作和具体动作为主；选择后与工作联动 |
| 详情 | 按需打开右侧非模态侧栏，可暂时覆盖辅助区域；错误、必要交接和任务材料按需读取，不默认展开审计元数据 |
| 文件阅读 | 替换中央工作区域的阅读视图，保留运行控制及 Worker 区；返回恢复工作选择、局部位置和焦点 |
| 窄屏 | 按阅读顺序重排，长内容可局部滚动；不挤成不可读的桌面多列 |

原型底部的演示场景栏、模拟状态时序及样例内容不进入正式工作台。产品布局与交互沿此基线实现，运行状态必须接入真实 API/Engine。

固定主工作区：顶部保留任务/运行选择、实际状态与最小控制；可收起导航退居次要；中央工作列表/紧凑时间线和 Worker 活动区同屏；常规详情用按需非模态侧栏，临时聚焦才用弹窗。原件阅读可扩大中央区，返回恢复现场。避免默认三列常驻、等权卡片矩阵、装饰性统计大屏和常驻聊天栏。

首版采用紧凑时间线，不把先后顺序当依赖，直接显示必要依赖和阻塞关系。DAG 对比后置：只有实际并行追因暴露问题时，才用同组任务比较，不作为首版实施前置。用户确认的是当前布局，不是时间线优于 DAG 的实测结论；已有任务依赖图也不等于工作 DAG。

桌面壳体不随长内容增长，任务文件和命令输出在命名面板内滚动；短屏、窄屏和放大文字允许重排，不能靠裁切或缩字号实现单屏。焦点、键盘/Escape/返回行为优先于动画，数据刷新不抢选择或滚动位置。

采用原型的雾白浅色与石墨深色双主题，浅色为默认；语义角色、密度和排版以原型为视觉参照，必要的可读性/无障碍调整在正式页面验证。当前工作与关键状态高于元数据，状态同时有文字，不能只靠颜色。沿产品 CSS 变量维护一份数值来源，不引入第二套主题规范。

动效限于选择定位、面板入退和实际状态变化；快速切换可中断，减少动态模式保留最终状态、移除非必要空间移动及循环。不以动效结束作为业务生效条件，不做虚假进度、预计暂停倒计时、思考动画、永久流光或粒子。简单效果先复用 CSS，无实际需求不新增动画库。

## 5. 前后端能力与必要缺口

核查代码基点 `18694a1`。S1–S4 实际交付分别见 [S1](../../../.scratch/s1-task-contracts-and-onboarding/spec.md#交付验证)、[S2](../../../.scratch/s2-attempts-and-worker-handoffs/spec.md#交付验证)、[S3](../../../.scratch/s3-evidence-and-shared-knowledge/spec.md#交付验证)、[S4](../../../.scratch/s4-task-policies-and-delivery/spec.md#实施与最终验证)。部分历史入口的未实施文字已滞后，不据此重复建设。以下是设计与开发依据，不是产品界面内容。

| 用户操作 | 复用基础 | 必要代码/接口缺口 |
| --- | --- | --- |
| 看工作状态与依赖 | Observer 的 Run/Attempt、work_id、dependencies、blocked_by、resource_wait | 补按需工作摘要集合，避免逐项拉取详情；修正未 decided 一律投影 unknown 的粗粒度；旧 node_waiting 不能代表当前仍阻塞 |
| 看 Worker 当前具体动作 | Call、工具事件、JSONL 游标读取和现有前端轮询 | 贯通工作与 Call；提供活动摘要及按需增量明细，保留动作名、对象、开始/结果关联和有效时间；修复在途日志关联问题 |
| 查看错误、交接、任务文件 | calls.input、调用结果、现有 artifact/content 局部读取 | 按所选调用读取必要输入输出，明确指向相关任务材料；提供可读错误，恢复选择/位置/焦点；不暴露内部完整上下文包或原始事件 |
| 理解结果/未完成原因 | S4 已有完成结果、交付候选及未完成原因 | 只呈现面向用户的结果、原因和产出链接；撤回证据、主张版本历史及审核导航页面 |
| 暂停/停止 | control 事件、Run 状态、Engine 派发边界与取消处理 | 现 API 仅 GET；补受控写入口、请求关联及实际应用结果，明确失败和未知，不由页面直接写账本 |
| 继续同一运行 | Engine.open_run/restore_run/run/reconcile、CLI 显式 run_id、项目单写入约束 | 补可靠启动/重入及启动失败反馈、恢复生效事实；不能只设 control=run，也不能将 active 当作恢复完成 |
| 保持清爽 | 现有 React 组件、URL 选择、主题变量 | 移除 Sources、digest/sha256、内部 ID 与元数据面板；限制材料/输出入口，不能以通用文件列表重新暴露内部材料 |

源码入口：[adapter](../../../opc/observer/adapter.py)、[API](../../../opc/observer/api.py)、[DTO](../../../opc/observer/models.py)、[Engine](../../../opc/core/engine.py)、[Ledger](../../../opc/core/ledger.py)、[CLI](../../../opc/cli.py)、[web App](../../../web/src/App.tsx)、[组件](../../../web/src/components.tsx)、[前端类型](../../../web/src/types.ts)。Python DTO 允许额外字段，不能把前端未消费误判为 HTTP 丢字段。

必须带入实施的三个具体判断：

1. **实时日志关联缺口（源码推导，未运行复现）：** 未完成调用的 call_dispatched 没有后端 session_id，adapter 回退采用 ArcHa Call ID 与日志头的 session/thread ID 比较，可能导致调用进行时日志不可读。应补可靠的当前 Call—本次日志—后端会话关联，保留归属检查，不用放宽匹配或采用最近日志规避问题。
2. **活动投影缺口：** 当前消息 state 为空，Call.last_activity_at 为空；DSH read 目标在 input 中未提取，命令结束的 text 优先 output 可能遮掉命令本身。需要补明确的活动投影，而非读取文本猜状态；DSH 仅核查代码/假 CLI 夹具，不宣称真实后端通过。
3. **恢复反馈缺口：** Engine 在 reconcile_calls/hard_check/backfill_history/reconcile 之前写 active，不能据此宣称恢复已完成；open_run 或获取执行权还可能在运行循环错误处理之前失败。命令边界需覆盖这些失败，提供收到、恢复中、生效或失败的关联事实；这是请求反馈，不是另一套 Run 状态。

### 接口范围与责任边界

继续复用 `/api/observer/v1` 的 Run、Attempt、Call、messages、artifact/content 读取契约，按需要增补工作摘要、活动摘要和必要交接查询。工作摘要与活动刷新不全量读取原件；明细用现有游标/局部读取，首次进入也不能要求先遍历所有历史日志才看到最近活动。具体分页与摘要实现留到规格，不能为界面复制一套事实库。

新增控制命令入口与请求结果查询，逻辑输入包括明确目标运行、动作及请求关联身份；输出表达请求反馈、实际运行情况及可读失败原因。具体 URL/字段不在本简报冻结。只读 GET 不触发执行；命令由运行端受控接入 Engine，前端不持有第二套调度逻辑。运行进程承载、退出与重连方式需在实施规格中明确，不能仅启动一个依赖 HTTP 请求存活的执行任务便算完成。

复用现有事件与单写入约束，补必需的控制请求/结果关联及恢复结果事实，不增加控制数据库。相同请求重试、重复点击、多页提交不能启动两个执行者；已在运行返回实际情况，占用时明确告知，不暗中排队。请求返回无需等待整个运行结束。观察失败不改写工作结果；实现内部仍需准确身份、版本及恢复记录，但不向界面提供审计阅读入口。

## 6. 最小原型范围与完成判断

最小原型是一套共享壳体与两条连贯操作路径，不是全站重写或两套完整展示系统。用户随后已授权实现本原型，交付与验证见 §9。

| 切片 | 必须能观察/操作的内容 |
| --- | --- |
| 工作现场 | 工作状态与 Worker 活动同时可见，关联选择，必要依赖及具体动作；首屏不堆卡片或内部材料 |
| 阻塞诊断 | 错误、必要交接、相关任务文件/产出、返回现场；覆盖调用重试与一次并行工作追因 |
| 暂停/继续 | 请求未确认、在途收尾、实际暂停、恢复中、恢复成功/失败、状态暂不可确认；成功结果不重复执行 |
| 停止最小分支 | 请求收到、实际停止、终态未知；不将停止显示为交付成功 |
| 主题/交互 | 浅深主题候选、面板显隐/阅读、键盘与焦点返回、快速开关、减少动态、窄/短视口及长中文 |

采用当前协议真实记录或清楚标明的夹具。夹具只能验证交互和展示，不算真实控制通过。API/Engine 的后续验证要覆盖在途日志可读、命令关联、暂停无后续派发、恢复不重做成功调用、重复请求/断连不双重启动、停止未知终态、观察失败不改业务结果。已有 [Engine 控制测试](../../../opc/tests/test_engine.py) 与 [并行控制测试](../../../opc/tests/test_attempt_dag.py) 是复用基础；不运行正式研究考试。

当前原型已获确认，首版不再要求 DAG 对比。若后续实际任务出现并行追因困难，再比较同组任务的定位路径、依赖误认和现场返回，不能只凭截图或动效决定增加第二套主屏。

完成判断：两条路径可走通，控制反馈不冒充实际生效，工作与调用状态不混淆，关键内容清楚可读，返回不丢现场，所有可达界面均无证据/审计/哈希及内部校验材料。原型需证明布局与交互，真实接口切片需另证明运行控制；两者不得互相冒充。

## 7. 减法、被替代决定与剩余未知

- 2026-11-01 用户允许调整视觉与布局，替代早期“不全面重做 UI”的限制；业务契约仍复用。
- 用户明确关注工作与 Worker 两类状态，替代仅工作主区、Worker 藏于详情的方案；具体活动而非单一忙闲标签已确认。
- 用户禁止证据/审计/哈希展示，替代早期证据、主张历史、来源和完整原始事件导航提案；不把撤回内容藏到高级入口。
- 首个原型同时覆盖诊断返回和暂停/继续，替代先做单一诊断视觉切片的顺序；停止保留最小控制分支。
- 不做知识编辑、手改 DAG、自由停靠、任意实验启动、主题编辑器、3D/装饰大屏、工具级断点、进程冻结、自动强停、恢复向导、第二套运行/知识状态库或 Worker 状态报告。

剩余未知限于：端点/字段与控制请求关联细节、运行进程承载、实时日志关联修复的运行验证，以及真实内容下的布局与可读性验收。它们是后续实施规格的输入，不重新打开已确认需求。只有实际使用表明固定布局或时间线妨碍核心任务，才重新考虑相应扩展。
