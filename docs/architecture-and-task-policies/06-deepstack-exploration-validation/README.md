# S6 DeepStack 建模探索验证

状态：最终验证方向已建立；方法从 S0 开始讨论，正式执行等待 S0–S5 必要工作完成。

入口：[总规划](../ArcHa_Phased_Development_Plan.md)。依据：[整体文档 §4](../ArcHa_Overall_Architecture_and_Task_Policies.md#s04)、[§10–12（起点）](../ArcHa_Overall_Architecture_and_Task_Policies.md#s10)、[§15–18（起点）](../ArcHa_Overall_Architecture_and_Task_Policies.md#s15)。

## 目标与依赖

由完成改造的 ArcHa 自主探索 DeepStack 的底层建模方法，弄清约定范围内从输入、参数和局部模型到最终输出的关系，形成可核查的解释与未知边界。

依赖 S0 的测试方法、S1–S4 的运行闭环与 S5 的调试整合。**框架开发及必要集成验收完成后，才开始正式 DeepStack 测试。** 前期可以完善方法和接口要求，不开展此项研究，也不预先规定研究答案。

对象是 DeepStack 的模型与实现行为。相关发现能否解释实际硬件，需要另外的适用证据；此阶段不把模型输出自动当作硬件真值。

## 测试方法怎样提前准备

方法原则以[总规划 §4](../ArcHa_Phased_Development_Plan.md#deepstack-test-method)为共同入口，由 S0 讨论收敛。后续各阶段只补充其能力对正式测试的影响：

| 前期方向 | 为最终测试准备什么 |
| --- | --- |
| S0 | 用途、研究范围、信息边界、交付与证据核对方法 |
| S1 | 测试意图到执行合同的映射、授权和实际准备条件 |
| S2 | 计划与实际执行的关联、原件位置、交接及恢复方式 |
| S3 | 结论、反证、未知和审核的记录及后续消费 |
| S4 | 研究工作选择、成果接纳、未完成状态与终验规则 |
| S5 | 人能沿 trace、上下文和证据定位研究与流程问题 |

不要求预制完整探针矩阵、隐藏答案打分器或固定实验轮数。研究过程由 ArcHa 根据证据选择具体案例和方法。

## 正式执行时的工作方向

- 核对实际 DeepStack 版本、环境与允许材料，落实已讨论的任务合同。已有[项目登记](../../../benchmarks/deepstack/README.md)和[任务入口](../../../benchmarks/deepstack/TASK.md)可复用；当前登记不证明环境已可执行。
- 冻结用于本次测试的 ArcHa 版本及必要执行条件，开展范围明确的自主研究，保留实际计划、动作、输入、观察、解释和修订关联。
- 对关键建模解释给出可核查依据，区分源码/文档事实、运行观测与推断；根据主张采用独立参照、受控变化或新案例核对，不让作者自测替代全部验收。
- 检查新证据是否真的改变后续决策，调试工具能否看清交接、待分析材料、反证和终验缺口；研究成果和框架行为分别报告。
- 出现框架缺口时回到对应阶段修复，保留失败与变更依据，只补做受影响验证。出现研究未知时如实保留，不静默降低标准或把它改判为框架故障。

## 预期产出与结束条件

正式测试应产出约定范围的建模解释、关键结论与证据入口、可重放方法、适用条件、反例/未知，以及对 ArcHa 的实际反馈。说明哪些关系已核对，哪些只是暂定解释；仅能运行官方例子或列出函数调用不足以说明目标完成。

必要交付通过阶段需求约定的验收才完成；环境受阻、预算退出和研究未决分别报告。只有合同事先允许且证据满足要求时，才可以有边界的未决交付结束。

本轮不强制另建两个真实项目，不默认做直接 Agent 对照、论文全量复现或 DeepStack 性能优化。若要宣称泛化、准确性或效率优势，再补与该主张相匹配的验证。
