## 四入口的交接

| 入口 | 接受什么、负责什么 | 交付与停止边界 |
| --- | --- | --- |
| Map | 开放方向、已有材料与任务关系；组织方向、依赖、备选和重开条件 | 地图及稳定任务目录。只表示方向/简报准备进度；有任务占位或 Brief 不证明依赖成果可用。不自动 Onboard 或执行 |
| Task | 明确任务目录及需求；工程任务可直接进入，无需地图。明确用途、In/Out、交付、验收、权限及重要未知 | Brief 与其来源；调用 Onboard 后核对意图和合同的对应关系，交接实际 task ID/revision。目标或验收冲突回此处理，不由运行时猜测 |
| Onboard | Brief、默认策略及实际领域/环境能力；解析契约，接入工具、评价与原件保存，完成必要准备检查 | 指定 revision 的候选契约、准备证据和 ready/未就绪原因。意图不变的路径、依赖、接入故障在此修复；不能替用户降标准，也不开展正式研究 |
| Loop | 明确任务和 revision，或明确的历史 Run；检查授权、就绪状态及恢复兼容性 | 新建或续接 Run，执行范围内的计划调整、反馈与交付。改变目标/验收回 Task；跨任务方向/依赖重整回 Map；接入故障回 Onboard |

这四个是职责入口，不是四次强制人工确认或四个新服务。Task 可自动调用 Onboard，Loop 可回用 Onboard 修复已授权准备事项；“本次只准备”仍须停在准备完成。地图依赖应引用实际需要的成果及版本，缺失时阻塞消费该成果的工作；不能用地图的 done 标签代替输入可用性，也不要求整个上游任务完结才允许消费已具备的必要成果。

## revision 的创建、冻结与生效

1. Task 身份持续稳定。首次可执行表达在 Onboard 生成 `r0001` 候选；准备阶段可原地完善，准备检查或审核本身不冻结候选，失败后修改和重试沿用同一编号。首次绑定执行 Run 时冻结；不保存每轮草稿文件，也不承诺完整重放草稿修改过程。
2. 已冻结契约的目标、范围、权限、交付或验收含义改变，以及已冻结的输入/评价资源或策略契约改变，需要新 revision。已冻结版本保留；后续修订分配未占用的下一编号。候选尚未冻结时可按第 1 条修改，但改变目标或验收口径仍须用户确认，已有明确授权无需重复确认。
3. 普通实验选择、假设调整、范围内代码修改、下一步计划变化不创建 revision。负责修改 Brief 的 Task 入口结合修改内容判断：明确的排版、错字、导航整理直接处理并更新来源关联；实质改变目标、范围、权限或验收则按契约变更处理；只有含义确实不清且影响执行时才询问用户。复用已有交接记录，不新增语义审查文件或独立审核 Agent，Engine 不重复判断自然语言含义；字节摘要变化本身不等于目标改变。已冻结合同文件自身不原地修补。
4. Onboard 的 `ready` 只证明该候选及指定准备输入通过必要接入检查。Loop 在已有执行授权下，校验明确版本、来源一致性、必要输入、冻结资源及能力后，由 Engine 保存实际解析值与来源，并绑定 Run；此时该 revision 对该 Run 生效。失败不启动正式 Worker，也不切换旧 Run 的契约。
5. 不新增人工维护的“当前生效版本”文件。Task→revision 交接复用 `DECISIONS.md`，准备与生效事实复用 ledger，Run 的实际配置复用 `frozen/`。编号最大只说明最近候选，不能意味着生效。每个 Run 只有一个执行 revision；同一 Task 的旧 Run 仍解释为它原有的版本。
6. 准备回执必须关联 task ID、revision、检查时的内容摘要和实际检查的资源身份，复用已有账本保留检查与审核记录。同一候选修改后，旧回执不能为新内容背书，只补查受影响部分；新 revision 的 pending/ready 不覆盖旧版本的准备证据。冻结后资源变化同样按影响补检；不因查看页面或导航文字变化重新计算全库摘要。

推导：**S0 事实**是 Run 固定引用一个 revision，已执行事实不改写；**实施前源码事实**是底层曾自动选最新目录、准备回执按 Task 选最新；因此 **S1 决定**是让生效与恢复绑定明确版本，而不是增加全局 active revision。竞争方案“始终使用最新版本”实现短，但创建 r0002 草稿就可能改变 r0001 的续接入口，不满足既定约束。用“r0001 暂停期间创建未就绪 r0002，再恢复 r0001”的小案例区分两者。

## 配置与就绪的最小规则

- 贯穿原则（2026-10-31 补充确认）：轻量化、渐进式披露，不做过度防御，不产生额外中间文件。讨论结论直接维护本专题；运行事实复用已有账本与快照，默认只展示行动所需摘要，细节按需展开。
- 保留 JSON 执行配置和 Markdown Brief；不在 S1 引入 YAML 转换或任意 Profile 插件。Profile 为开发、调优、探索提供有版本的默认策略，不赋予权限，不把 Activity 变成固定流程。三类意图可表达不代表三类能力已实现。
- 普通默认值按 Profile → Task 显式覆盖 → 允许的本机绑定解析。目标、验收与权限不由本机配置覆盖；用户/项目硬限制取共同允许范围，`null` 不取消已有显式上限，冲突给出来源与原因。预算沿 S0 累计，不因 revision、Run 或进程重启清零。
- 预算归属（2026-10-31 确认）：首版按 Task 累计，包含准备及各 revision、各 Run 的用量；项目上限另作共同约束，不引入跨任务共享预算池。追加授权提高总上限，保留已用量。当前默认 token 无上限（`max_tokens: null`），仅以 2 小时（`max_wall_seconds: 7200`）作为预算约束；既有显式硬限制仍须遵守。实际用量及来源从既有账本读取。
- 冻结影响执行与解释的实际值及来源版本，复用 Run 快照；本机路径/凭据仅保留必要引用，不复制秘密。恢复时不能用后来模板默认值重新解释历史配置。
- `pending` 表示仍有可自主完成的准备工作；`external_blocked` 需有失败证据、缺失外部条件与下一步；显式预算下无法可靠计量则记录实际计量阻塞。未实现的执行能力也保持未就绪，不能靠解析成功放行。
- 开发允许产品功能门尚未通过，但工具能真实执行并报告失败；调优需有可比较的测量通道和基线；探索需有材料读取、观察、证据保存及验收通道，不要求 Onboard 预先产出研究答案。必要独立准备审核仅按合同启用，不另设常驻 Reviewer。
- `execution_enabled` 是执行开关，不代表版本生效、环境兼容或任务完成。观察端默认展示 task/revision/run、就绪或阻塞原因及来源链接；字段来源、检查回执和原件按需展开，不增设总结 Worker 或第二本状态账。

## Run 新建与恢复矩阵

| 情形 | S1 行为 |
| --- | --- |
| 首次执行已准备 revision | 检查通过后新建 Run，冻结实际起点、契约与必要绑定 |
| 同 revision 暂停/受阻，条件已恢复 | 明确定位原 Run，通过兼容检查后沿用其 ID、历史、成果与累计用量；恢复须有继续执行意图，不能因查看状态清除 pause/stop |
| 控制器中断但 Run 未关闭 | 先确认无活跃控制器、获得既有单写锁，再恢复事实；不能直接把未完成工作当成功。工作级恢复交 S2 |
| 新 revision 开始执行 | 新建 Run；旧 Run/快照/失败报告不改写。起点显式记录，不暗中继承旧冠军或上下文 |
| 同 revision 的独立执行 | 在用户要求新一轮或已授权的明确工作流下新建 Run，保留累计预算；Run ID 不同不能单独证明实验独立 |
| closed，包括用户 stop、预算退出、完成或自然结束 | 默认报告原结果，不原地重新打开。继续工作走有依据的新 Run；失败终验的已授权范围内修复可新建修复 Run，关联失败报告并继承累计用量 |
| 多个可能续接的 Run | 指定 Run ID；仅有一个明确可续接对象时才可自动解析，不能跨 revision 按“最近”猜测 |

兼容性分三层，不用一个布尔值掩盖区别：

| 层次 | 必须成立的条件 | 不成立时 |
| --- | --- | --- |
| 可读与追溯 | 原身份、合同/快照、账本、结果和原件引用可读取 | 缺项照实标注；保留能读的材料，不补造历史 |
| 可恢复执行 | Run 未关闭；契约与权限一致；必要代码/输入/评价资源可定位；runtime 支持原记录；工具能力与资源条件符合契约；控制与预算允许 | 保留旧记录，说明具体不兼容项；可修复接入问题回 Onboard。不能自动升级、改旧合同或开新 Run 绕过阻塞 |
| 可复用测量 | 代码、输入、评价口径、工具链及相关环境满足该测量的可比性要求 | 保留旧观测，按影响重测，不把旧缓存标成新实测 |

环境变化不一律创建 revision：同语义的路径迁移、工具恢复可在核对并记录绑定后续接；工具链变化若仍符合原契约，可保留 Run、隔开旧测量并重建所需基线。若违反冻结评价条件、改变输入/权限/验收，需新 revision 和新 Run；无法判断兼容则阻塞受影响执行，不能仅因“重测冠军成功”宣布全部兼容。新增 runtime 是否支持旧格式必须由明确版本支持和夹具验证，不承诺任意旧版本都能恢复。

## 旧记录与已有特殊路径

- 旧 revision、Run、结果原位保留；不批量重写为新格式。新字段缺失显示 unknown/legacy；只有可从已有原件确定的关系才可追加有来源的兼容记录。旧式明确 Task/Brief 关系可补记交接，歧义不能按名称猜。
- 已部署 runtime 默认保持其版本；升级是单独的显式动作，复用现有锁和备份机制，不以仓库代码已更新推断项目已更新。旧 Run 可以只读但不能续接，这是允许的兼容边界。
- 历史 `revision="preparation"` 账本行保持可读和累计；新准备使用既有账本的 Task scope 事件与计量，不创建业务执行 Run 或 Attempt。
- 现有 `promote --standards-confirmation` 能对旧成果按用户确认的新验收 revision 重新判定，不创建执行 Run。保留为 **旧成果重验**，不得描述成旧 Run 切换契约或恢复执行；执行 revision 与验收 revision 分别展示，原失败报告保留。它不能改目标、执行输入、评价器或预算；需要继续工作时仍创建新 revision 对应的新 Run。细节与完成语义由 S4 承接。
