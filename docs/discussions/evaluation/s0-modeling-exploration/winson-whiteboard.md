### 已明确的共同关系：Revision 与 Run

用户纠正了前轮省略 revision 的说法：目标、权限或验收发生实质变化时，先起草新的任务契约 revision，经过相应确认与就绪检查后生效，再基于该 revision 新建 Run。草稿本身不改变当前 Run 的生效契约。已执行 revision、旧 Run 及其测量保留原意，不能原地覆盖。

Task 承载持续的任务身份；revision 承载版本化的目标、授权与验收；Run 引用一个已生效 revision，记录一次实际执行。同一 revision 可以支持多个 Run；新建 Run 不必然需要新 revision，单纯暂停/恢复通常继续原 Run。跨 Run 的研究连续性由 Task 与显式证据引用承担。Ramulator 调优题若开考后增补请求接收事件验收，应先形成新 revision，再开新 Run，新旧成绩注明各自口径。

依据：整体文档 §8.2 已区分 Task、Contract revision、Run、Attempt、Experiment 与 Measurement；§13.1 要求已解析契约快照冻结。现有 `opc/core/ledger.py` 的 runs 表存 `task_id`、`revision`、`task_digest` 和 evaluator/toolchain digest；`opc/core/engine.py` 在修订或摘要变化时要求 `--new-run`。现有检查是复用基础，不等于新的 revision 起草、生效与就绪流程已完整实现。工具链变化与旧数据可比性的细节留给迁移/验收讨论。

减法：本轮推迟全对象字段表、数据库迁移和新观察 UI；只确定这条边界，因为删掉它，跨阶段验收和恢复时无法判断旧数据是否仍适用。

### 已确认：Run、Attempt、Call 与 Worker 生命周期

用户已同意本节最终场景解释及职责划分：Run 引用生效 revision 并承载持续执行；Attempt 为有边界的工作轮次；Call 为一次完整 Worker 派发。典型 Attempt 按需包含 Expert、Designer 等调用；Codex/DSH 默认按角色 Call 启动新 CLI 会话，会话内部的模型请求、工具操作和局部调试不另算 ArcHa Call 或 Attempt。创建 Run/Attempt、保存结果、直接执行评价脚本不自动启动模型。Onboard 和终验调用分别归入准备/交付范围，不强制创建普通 Attempt。以下前序“待确认”“建议”等表述的确认状态以本段为准；未批准扩大实现范围或启动正式考试。

**回查原始讨论后的建议：** 保留 Task → revision → Run → Attempt 的关系；Attempt 作为基本工作单元，Call 作为基本 Worker 派发单元。Run 是某个 Task 在一个生效 revision 下的一次持续执行，可跨进程启动、暂停与恢复，包含多轮工作，直到完成交付或按明确原因关闭。Attempt 是一次有界的决策/工作轮次，将计划、实际起点、执行、必要验证和产物记录关联起来；完成不必代表提速、假设成立或结论已解释。每轮以可交回专家判断的成果为边界，不按文件、命令、模型请求或上下文压缩次数切分。简单任务允许只有一个 Attempt。

Worker 生命周期需要分清角色、适配器对象和实际 Agent 会话：Expert/Designer 是可跨 Run 使用的角色定义；现有 Engine.workers 缓存适配器对象；Codex/DSH 适配器默认每次角色 Call 创建新会话。典型 Attempt 内先调用 Expert（解释上一轮并规划本轮），再按需调用 Designer 与评价工具；下一个 Attempt 的 Expert 调用可补上一轮结论。一个角色 Call 内可有多步工具使用和局部调试，不因这些内部步骤自动创建 Attempt。Reviewer 仍按需，Evaluator 可为程序。建议首版沿用按 Call 隔离会话、通过持久化材料承接经验的方式，不引入整个 Run 常驻的大会话或额外常驻团队。

依据（本轮只读核查，未运行模型）：原白板 `docs/discussions/opc/winson-whiteboard.md` 的 2026-10-25 用户纠偏及“结论的生成时机”“续用中间版本”；整体文档 §8.1–8.2、§9.1–9.2、§14.2；工作树基于 `d93ef12`，核对 `opc/core/engine.py::workers/attempt/run`、`opc/adapters/codex.py`、`opc/adapters/dsh.py`。原文强调两个职责角色而非两个永久实例，并已提出每轮记录与单次调用身份。本轮建议修正前一答复将 Attempt 主要解释为日志编号的不足：底层可以用事件关联实现，但“本轮派发什么、在哪个起点执行、结果如何交接”的业务边界应保留。尚未将建议标作用户确认或修改运行代码。

竞争方案：把每轮工作都叫 Run 可以少一个名词，但整体执行的暂停恢复、停止原因、跨轮候选选择仍需另设容器；直接沿用现有 Run/Attempt 更少迁移成本。全 Run 复用同一会话可能减少上下文重建，但角色权限、恢复和上下文增长须另行验证；本轮没有效果实测，不能宣称按 Call 新会话效果更优。减法是复用当前角色与调用结构，不新增层级、强制逐轮审核或每步工单。

本轮补充场景解释：Call 不是新增业务审批层级；整体文档 §14.2 已定义 call_id，现有 WorkerCall 和 worker_call 事件记录实际角色调用。正式迭代的关联是 Run 引用 revision、Run 包含 Attempt、Attempt 关联角色 Call；Onboard 和终验调用可属于准备或交付范围，不强制归入普通 Attempt。Ramulator 示例中，r1 下的 Run 1：Attempt 1 由 Expert Call 1 提出基线诊断，Designer Call 2 执行并保存证据；Attempt 2 的 Expert Call 3 解释前轮结果并计划优化，Designer Call 4 实施，程序评价器验证。每个 Codex/DSH 角色 Call 启动相应 Worker CLI 会话；创建 Run/Attempt、保存记录及直接跑评价脚本不会自动启动模型 CLI。单次 CLI 会话内部可有多次模型请求和工具操作，不因此增加 ArcHa Call。当前源码核对包括 CodexWorker.propose/implement → _run → Process，以及 onboard 的准备 worker 调用；没有实际启动 CLI 或修改实现。

用户进一步质疑已有 Run 是否还需要 Attempt。本轮判断：对于一次执行只产出一个结果的系统，Run 可以足够；ArcHa 的一个 Run 会连续产生多个候选、测量和接纳结果，需要能定位其中一次派发工作的起点、结果与中断状态。建议保留轻量内部工作记录，沿用现有 Attempt；名称、独立表或完整公开对象并非必要。若用 Run 事件加工作关联 ID 同样满足这些需求，也可作为实现方式。不要为了概念完整性让用户管理 Attempt，或把每次阅读、思考、工具调用都拆成 Attempt。它与专家假设没有固定一一对应关系。当前为建议，尚待用户决定。

本轮源码依据：`opc/core/engine.py::reconcile` 使用未完成 Attempt 定位中断，恢复已发生的 champion 更新或保留成本并标记 abandoned；候选保存、评价及结果接纳也按 Attempt 关联。这里证明的是局部工作身份有实际用途，不是现有全部 Attempt 字段和生命周期均应原样保留。保留与简化边界在 S2 收敛。

建议沿整体文档 §8.1–8.2：Attempt 是从明确起始状态出发、围绕一个工作目标、最后保存结果的一次有边界尝试。一次尝试可以修改代码并测多个负载、只做独立复测，或只分析已有证据；不强制一轮改代码、一个分数或一次模型调用。实际测量分别关联具体代码、输入、环境和原件；复用缓存只引用既有观测，不能冒充新实测。复杂实验跨多次 Attempt 时可沿用问题/实验关联身份，但本轮不展开其全量字段。

Ramulator 例子：一轮改变调度扫描内部实现，然后对多类输入重复测量，是一次 Attempt 产生多条观测；另一轮只定位退化原因，也可形成有价值的 Attempt，不必制造代码补丁或额外测量。依据现有 `opc/core/engine.py` 的 evaluate_commit/repeats/cached 路径与 `opc/core/results.py` 的缓存标记，可复用已有计时和原件基础；通用 Attempt 的接纳/状态分离留待 S2–S4。当前是语义建议，不表示实现已完整支持。

1. 研究用途已确认：解释 DeepStack 怎样建模；不要求独立简化模型或架构优化成果。建议解释覆盖输入、局部估计、组合关系、输出及假设边界，并让关键主张可追溯、可核对；此验收细化待讨论。
2. 全流程范围已确认须有整体架构与主要模块覆盖；具体模块清单、代表性链路与各部分证据深度尚待收敛。
3. “代价函数”：局部性能估计、DSE 目标/可行性约束，还是另建预测模型时的拟合损失？三者不能混称，未确认要求拟合模型。
4. 信息边界：建议允许公开源码、文档、接口与运行观察，闭源部分保留未知；用户是否另有教学或辨识目标？
5. 验收：哪些关键关系必须有可复查证据，哪些未知可以作为有边界的未决交付？拟合一致不证明内部机制唯一。
6. 自主性：人规定目标、证据与资源边界；Agent 选择假设、探针、案例与后续路线。小测试是独立任务还是一个探索任务的里程碑，待定。

竞争解释示例：带宽变化后输出不变，可能是计算瓶颈，也可能参数未传入或路径未启用；需要调用链证据及能区分这些解释的干预，不能只凭曲线下结论。

## 减法与返回点

- 推迟所有算子/所有架构覆盖、论文全量复现、全面精度评测与独立真实项目；当用途要求泛化或硬件准确性时再加入。
- 不把更多小测试等同于更多预设步骤；保留自主选实验的空间。
- 不要求唯一还原不透明实现；若用户目标明确是内部精确公式，需要重新判断可得证据能否支撑。
