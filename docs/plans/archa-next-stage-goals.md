# ArcHa 下一阶段方向：先建立研究实践，再改进框架

记录日期：2026-10-29

文档性质：讨论结论、研究方向与待验证目标。它不是已经批准全面实施的规格，也不规定评分器、验证器或统一硬指标。

## 一、推进顺序与目标

下一阶段先在 Linux 上逐步搭建 DeepStack 测试平台，用当前 ArcHa 开展具体研究：自行构建 cases、选择观测点、追踪调用与执行链路，逐渐形成有依据、注明适用范围的硬件规格与性能建模行为解释。等真实任务暴露问题后，再逐项优化 ArcHa 的交接与执行流程。

用户已报告在 Linux 服务器部署 DeepStack。本次整理未访问该服务器，未核实部署路径、源码版本、依赖或实际跑通情况；没有启动 DeepStack 实验，也没有修改 ArcHa 实现。文档提交仅记录后续方向。平台工作应从已有部署继续，不把“已部署”写成“已经验证可用”。

改进目标是研究过程是否连贯、观察是否可信、读取的材料是否切中问题、经验能否帮助下一次判断。token 和时间消耗不作为本阶段的目标；它们至多是定位重复读取或无效往返的辅助信息。

推进顺序如下：

1. 在现有部署上逐步确认一个可理解、可观察的调用路径，说明输入、公开接口、关键计算和输出各自代表什么。
2. 使用当前 ArcHa 围绕真实疑问构建小案例，保留对判断有意义的原始观察和研究经验。
3. 从实际执行中识别问题：信息是否断在角色交接处、计划是否跟不上现场发现、旧反证是否难以发现、重要原件是否丢失。
4. 一次针对一个已经出现的问题调整框架，再用相同或相关案例比较。研究对象、输入和框架变更分别说明，避免把平台变化误当成框架改进。

本文件只确定上述方向与边界，不重设计整个测试平台。

### 下一阶段的六步路线

以下为推进路线，具体开发由实际问题决定，不表示现在全面实施，也不要求先补齐所有候选实验。

| 阶段 | 主要工作 | 产出与推进条件 |
|---|---|---|
| 1. 平台资格与观察边界 | 从已有 Linux/DeepStack 部署继续，核实版本、入口、公开与隐藏材料边界、资源及基线能否运行 | 一条可理解的调用执行链，必要观察和未知项；先能区分依赖、内存或环境失败与研究问题，再进入案例比较 |
| 2. 固定现状做真实任务 | 固定当前 ArcHa，用 DeepStack 加一个构建任务，让 agent 自构 cases、选择探针，留下必要产物 | 顺利、失败和简单案例的事实基线；当具体交接或执行困难可以用原件说明时，进入相应局部改进 |
| 3. 补薄模板与观察接口 | 按实际困惑区分材料内容、交接选择、状态语义或观测缺口；先补最小表达和 runtime 机器契约，不做 UI | 接手者能理解材料，外部能区分关键状态；不要求其他模板或平台都齐备才继续 |
| 4. 一次改变一个因素 | 分别试验默认阅读与经验、内层连续研究及正式评价回传；外层 supervisor 的介入作为后续独立变量 | 每项改动有一个已出现的问题和可比较案例；不同时重写分工、记忆、评价与展示，能明确保留或撤回什么 |
| 5. 同题及新条件回归 | 比较当前 ArcHa 与改进版，必要时加入同模型直接 agent；逐例观察收益、无效和退化 | 解释改动适用于什么条件，是否依赖额外提示或经验；有相反案例也保留，证据不足则暂不下架构优劣结论 |
| 6. 只读 dashboard | 复用稳定的自动事件与产物接口，展示任务、研究阶段、worker 行为和观测缺口 | 确认状态与事件含义后再做界面；默认摘要、按需追查原件，不要求 worker 为 UI 写状态材料 |

路线允许根据实践小步往返。首批优先 DeepStack 加一个小型构建任务，待平台与观察方式可靠后再引入调优；第七节给出候选，不同时搭建全部项目。

## 二、DeepStack 的研究边界与认识层次

### 当前能据官方材料确认的范围

DeepStack 官方将项目描述为分析型建模工具；`main` 包含后续修正，论文复现使用的 `ae` 分支有不同定位。具体采用哪个版本，要在实际研究开始时从用户部署核实，不能用远端文档替代服务器事实。[DeepStack 官方 README][deepstack-readme]

其发行版混合不同许可：除列明例外外，源码等材料采用 Apache-2.0；若干预编译 `.so` 使用独立专有许可，第三方文件还需看各自声明。公开可读不等于所有组件适用同一授权。[官方 LICENSE][deepstack-license]、[许可范围说明][deepstack-licensing]、[第三方声明][deepstack-third-party]

研究使用前提已确认，相关工作内部进行；本公开规划只记录通用方法和公开来源，不披露内部研究细节或非公开参数。许可不作为当前阻塞，不要求重复确认。公开发行版的二进制条款 §4(b) 仍作为适用范围背景保留，不把内部安排扩大到公开传播、商业使用或其他未说明用途。[公开二进制许可背景][deepstack-binary-license]

### 接下来如何形成可信解释

把研究内容分成三个层次，并在现有研究文字里明确表达，不为此另造一套索引文档：

| 层次 | 可以形成的认识 | 需要保留的界限 |
|---|---|---|
| 可读源码中的机制 | 公开公式、分支条件、数据流、单位转换、接口及调用关系 | 指明它描述的是哪部分软件模型；不能据此声称知道受限二进制内部实现 |
| 已说明内部授权范围内的接口观察 | 在具体输入与配置下，文档化输出表现如何，是否支持当前解释 | 先区分观测、假设与未确定部分；对非公开内容的研究遵循已说明的内部安排，不扩大到未说明用途 |
| 对硬件行为的推断 | 在公开模型假设与给定条件下提出性能解释、可检验的规格主张 | 分析模型预测不等于 RTL 行为或实测硬件真值；需要另外的独立证据才能提升结论强度 |

官方还提供接受调用者自有参数的公开配置接口，可优先用于机制理解和自定义案例；具体适用范围仍以相应源码和许可为准。[公开架构配置源码][deepstack-custom-profile]

若观察了公开实现中的答案，再构建案例说明其行为，应称为源码辅助分析或机制复核，不能叫严格盲测。若将来需要评估未知机制推断，应明确哪些实现信息可见、哪些问题尚未知，并遵循已说明的内部授权范围；本阶段不预设隐藏答案任务。

每个案例先问清一个问题，例如某项输入变化经过哪些公开计算路径影响输出、某个异常来自条件变化还是理解错误。观测点应服务于区分解释，避免为了“追踪完整”而读取或保存所有文件。硬件规格可以先写为条件性主张：哪些输入和前提下成立、由哪些公开机制或观察支持、哪里仍不能确定。

## 三、源码审计基线：当前 ArcHa 已经具备什么

本次源码审计核对的 ArcHa `main` 为 `8b70578be3aa9ee63538271993e67bf4aa4aee3a`；后续再次查询远端，仍是同一提交。EAT 对照使用 `737e1665eeeffd3fce35d319174f88ea4613d7aa`。这些是框架分析基线，不是用户服务器已部署版本的证明；目标项目的 `.opc/runtime` 快照和已安装技能需要在实际工作时另行核对。

本规划追加到已有 PR #10，准备文档时其分支 head 为 `978ca22c`。该 PR 已增加多研究专题及明确任务目录入口：地图可独立建专题，task/loop 按给定目录接续，并复用原有决策记录。这改善了选中哪一个研究专题或任务，但不等于已经改变下文审计的 worker 输入和研究反馈时序。下面的源码判断仍对应上述 main；PR #10 的新增入口以其[使用说明][archa-topics]为准，不能把旧的单一入口假设写成当前设计。

### 上下文不会全部自动继承

- `archa-map`、`archa-task` 的完整主会话对话不会由 Engine 自动交给实验 worker。地图、discussion 和全部 evidence 也没有被递归拼进正式 worker 输入。
- `brief-check` 读取来源文件做来源校验，返回路径与摘要信息，不把地图正文作为模型输入。onboard 接收完整 brief；指南要求只补读本任务相关的地图与证据，缺失或冲突时才扩大调查。
- 正式 expert 被要求读 `research.json`；designer 收到 plan 和部分目标、路径及 parent 信息，而不是整个 ctx。两者默认使用新的 CLI 会话。
- 原始 worker events、stderr 等是留档，不会默认全量回灌；expert 的短启动提示词也不代表其必读研究材料很少。

因此，现场若出现“把整个地图、任务调查或所有日志又读了一遍”，应从实际 prompt、研究材料和工具读取记录分辨：程序注入、技能明确要求、主会话转述，还是模型自行扩读。不能仅凭文件存在就认定它已经占用 worker 上下文。[brief 来源处理][archa-brief]、[onboard 阅读指导][archa-onboarding]、[角色提示词][archa-prompts]

### 当前已有跨轮反馈，不是完全没有研究闭环

| 已有能力 | 源码中的行为 |
|---|---|
| 连续实现与局部验证 | designer 可以在一次调用里读代码、局部测试、修复和再检查 |
| 失败反馈 | 有 plan 和 outcome 的失败尝试可进入近期 history；并非只给成功记录 |
| 保存实验事实 | 正式评价的结构化数据、失败状态和缓存标记先登记，再结束 attempt |
| 保留有价值候选 | candidate 在正式评价前保存，因此无收益或正式评价失败的候选仍可被选择 |
| 研究解释 | 后续 expert 可为尚未有 conclusion 的尝试写解释，不要求每轮清空全部待解释项 |
| 自主选版与停止 | expert 可选择已保存旧候选，也可以停止；非数值任务可以继续积累 working version |
| 独立交付审核 | reviewer 位于终验路径，并非每个 attempt 都新增审核角色 |
| 原件与恢复 | ledger、既有报告、最终回复和评价原件支持恢复；不依赖把完整会话重新塞给 worker |

designer 调用失败或 sandbox 失败发生在 candidate 保存之前，不能把“保存了失败候选”泛化为所有失败代码都保留。基础设施失败可能先阻塞，待恢复后再消费发现。[历史输入与结论][archa-context]、[执行及评价顺序][archa-attempt]、[恢复反馈][archa-backfill]、[终验 reviewer][archa-review]

前一轮还做过合成输入构造与三个现有离线测试，证明了部分输入路径和原件保留行为；这些不构成真实研究效果验证，也不是 DeepStack 平台已跑通的证据。

## 四、值得继续验证的接口与架构问题

### 从“文件很多”进一步看“为什么会默认读这些文件”

现有输入已有历史窗口、背景摘录和成果正文限制。更深的问题是选择依据：最近的记录未必与本轮问题有关，共享文档头部未必属于当前任务，README 链接很多原件也不代表必须展开所有原件。

目前 `results.snapshot()` 会扫描成果 README 的全部 Markdown 链接并展开一跳；正文有限制，但全部来源元数据仍会进入 snapshot。自动登记历史、旧 plan、人工结论和相关规格混在一个消费路径里。designer 又收到完整 plan，其中包含 expert 的历史 conclusions。改进的第一步应是改变默认阅读理由，而不是继续加一层长度裁剪。[成果读取][archa-results]、[designer 输入][archa-prompts]

| 阶段/角色 | 默认需要理解 | 有具体疑问再读 |
|---|---|---|
| 地图与任务准备 | 当前方向、任务范围、依赖与待定事项 | 相关讨论与调研证据；不因恢复任务而通读所有研究方向 |
| onboard | brief、合同映射与必要接入事实 | 影响合同的关键源码、相关 evidence 和源地图片段 |
| expert 或未来研究执行者的阶段入口 | 当前目标、默认工作状态、已有关键结论和反证、未决问题 | 对应主题的旧实验、原始数据、必要代码或异常日志 |
| designer | 本轮实施任务、相关验收和接口、真实 parent、编辑边界 | 相关代码、局部测试及本轮需要的旧发现 |
| reviewer | 待审核主张、要求和实际交付版本 | 对应实现、完整差异及原始证据；不能只依赖作者摘要 |

这里的“当前问题”是尚待解决的疑问，不是调度者预设的正确答案。

### 研究判断与现场观察被分给了不同角色

expert 的提示词要求它决定研究步骤，同时不要调查源码或原始日志；designer 接触实际代码和局部观察，却被要求实施既定 plan。designer 的最终回复是自由文本，不是模型被迫只输出一个字段；但 Codex/DSH adapter 只将其末尾文本包装为 summary，框架不会把其中的新假设、选版或评价请求解释成研究决策更新。

实际自由度需要分清：

- designer 已能连续调试、修改具体实现、增加范围内的局部诊断，并报告偏离。
- 它可以在推理和文字里否定原假设，但没有受支持的返回接口改变本轮 `base_attempt` 或 `evaluate`；框架仍消费原 expert plan。
- 正式测量方法和验收条件受冻结合同约束，不能把随意更改它们当作缺失的“自主性”。
- 框架没有通用的“实现是否忠实于假设”语义检查。范围内的实现即使已改变方法，也可能被保存，而历史 plan 仍是原计划；这可能造成意图与实际行为失配。
- 正式评价在 designer 返回后发生，结果进入下一次新 expert 会话。当前有跨轮反馈，但提出解释、观察异常和改解释的过程可能经历有损交接。

例如，计划认为某项收益来自访存改善，执行时却发现输入根本未覆盖预期路径。真正需要观察的是当前机制能否及时修改对照和研究解释，而不是能否继续按旧计划完成一个补丁。[提示词分工][archa-prompts]、[designer summary 消费][archa-designer]、[正式评价时序][archa-attempt]

### 选版顺序本身不是 bug

`Engine.context()` 先构造 expert 输入，expert 查阅候选证据后返回 `base_attempt`，引擎再解析 parent 并给 designer 建立工作树。expert 已有候选和证据引用，也允许选择窗口之外的已保存候选。

初始输入只能围绕已知任务方向、默认 working version、现有结论和候选入口组织，不能假定尚未选择的本轮 parent、新 experiment_id 或新假设。若要选旧版本或转向另一个问题，由 expert 在同一次调用内查证后决定；designer 才接收解析后的实际 parent。窗口外候选的可发现性可以改善，不需要因此增加一个预选版 agent。[候选与输入构造][archa-context]、[parent 解析][archa-parent]

### 失败发现已有通道，但事实与解释的延续仍有缺口

失败 summary、结构化实验数据和后续 expert conclusion 已可进入后续输入。需要验证的是重要观察是否真正留下：如果只存在于未持久保存的 scratch 文件，工作树清理后可能无法重新查阅；如果只出现在工具输出而未进入相关入口，下一轮未必知道该找什么。

此外，`save_conclusions()` 接受的是尚无 conclusion 的尝试。旧解释被新证据推翻时，不能经此接口直接替换旧 conclusion。现有成果 README/specs 可以表达更新后的认识，应充分利用；不必为此另建结论版本数据库。[结论保存限制][archa-conclusions]、[工作树清理][archa-cleanup]

## 五、待验证的研究执行方向

用户认可的待验证方向，是外层 supervisor 加内层研究团队，但需要重新划分当前 expert 的职责，而不是把完整 expert 复制到两层。

| 位置 | 主要职责与边界 |
|---|---|
| 外层 supervisor | 围绕开发场景确认目标、约束、阶段方向和是否需要转向；承接当前 expert 中较高层的判断，低频介入，不替内层每次定微计划 |
| 内层研究执行者 | 将局部 expert 与 designer 合并到同一个 agent：理解问题、选择相关材料和工作基线、提出假设、实施、观察、修改解释与方法，再形成候选或结论 |
| runtime | 提供可信的执行事实、工作版本、必要原件保存、正式评价和恢复边界；将正式结果反馈给同一研究阶段 |
| 独立 reviewer | 在需要独立判断的交付节点，核对要求、候选和依据，保留不同于作者的审核视角 |

外层交给内层的是当前要解决的疑问、目标和约束，而不是预定答案或每一步做法。内层如果发现目标前提不成立、需要越出当前范围或改变验收口径，应把事实和待决问题交回外层；范围内的假设修正和实现路径由同一执行者连续处理。外层也不需要默认阅读全部工具 trace 或所有旧实验，可以从现有材料形成当前视图，再按疑问查原件。

这不是永久长会话。问题已解决、范围需要改变、转向另一问题、真实阻塞或用户暂停时，可以结束阶段，依靠现有经验与原件接续。阶段边界取决于研究问题，不预设必须进行几次实验或写几份文件。

也不是简单拼接两段 prompt：当前正式评价在 worker 返回后运行，adapter 默认新会话。若要试验这种方向，必须考虑正式结果如何回到同一阶段，以及 runtime 如何消费实际采用的方案。仅把 expert 改名 researcher，却继续在评价后换一个不了解现场的新会话，并不能解决主要断点。

| runtime 应保持的职责 | 更适合由研究执行者判断的事项 |
|---|---|
| 授权范围、可写边界、冻结评价器与验收条件 | 先读哪段代码、查哪条历史、做什么局部诊断 |
| 候选与必要原件保存、正式评价、测量可比性 | 何时调整假设、补对照、承认未知 |
| 区分新实测、缓存、失败和未测 | 一个问题需要多少次观察与解释修正 |
| 用户暂停、恢复及真实权限条件 | 当前路线是否值得继续、何时换方向 |
| 既有正式交付与独立审核要求 | 哪些发现应进入共享经验 |

这是待比较的架构假设，不是已经证实优于当前流程的方案。Anthropic 关于合并子代理的文章提供了相近思路：按共享上下文与任务耦合考虑合并，同时保留验证、独立并行与权限边界的价值；它没有证明 ArcHa 应一律改成单 agent。[参考文章][fold-agents]

实现时应按问题逐项推进：可以先改善当前 designer 发现的写回与正式结果消费，再试验有界阶段内的同一 agent，最后依据场景确认外层 supervisor 的介入点。不会因为认可这个方向就立即重构调度器、会话、记忆与界面。

以下情况仍可能适合现有分工：规格稳定的简单实现、确定性的参数搜索、上下文相对独立的并行研究分支、严格不同的权限域，以及需要避免作者自证的独立审核。后续比较应保留简单任务作为退化反例，防止合并后出现无关探索或更差的执行纪律。

### 需要用真实案例辨认的潜在风险

下面是由架构方向推导的风险，不是宣称源码已经发生这些故障。只有观察到相应问题，才触发最小调整；不提前添加控制层或监控文档。

| 风险推论 | 可观察征兆 | 最小改进触发 |
|---|---|---|
| 外层与内层重复指挥 | 内层尚未完成可判定实验，外层反复改题、撤销工作或重写微计划 | 明确外层负责目标、阶段、跨路线资源及必要团队调整，内层负责技术假设与局部决策；不因一次低分自动换人 |
| 不同失败被归成同一种能力问题 | 假设不成立、实现 bug、测量错误、环境问题和接口丢信息都被解释成“worker 不行” | 从已有原件辨认原因；无法区分就保留不确定，不用重组角色掩盖原因 |
| 主张、实际代码与测量条件漂移 | 实现已偏离原 plan，却继续把收益归给旧假设，或把不同条件的结果并列解释 | 在已有记录对齐实际采用方案与条件；不新造哈希索引，也不允许改写旧事实 |
| 长程理解同时固化错误锚点 | 新证据出现后仍维护旧解释；换新 agent 后又重复已被否定的路线 | 观察能否修订认识和发现反证，不按固定轮次清空上下文；重试失败路线需说明条件变化或新证据 |
| 正式评价与解释、恢复错序 | 已执行但未解释被当成没执行，旧结果被当新测量，局部计时与正式条件混用 | 沿已有事件核对候选、评价和解释的顺序，区分恢复与有意重复实验；先确认事实，再决定是否修改恢复接口 |
| reviewer 只复述同源摘要 | 审核引用作者结论，却无法指出对应原件或关键反例 | 让现有 reviewer 直接核对证据；必要时先看目标、变更与测量，再读作者解释，不增加 reviewer 层数 |

## 六、共享经验、渐进披露与原始观察

### 复用现有位置，分清原件与认识

优先复用成果 README 的人工区与已有主题 specs；原始观测继续保存在已有 evidence/artifact 位置。自动运行登记仍是执行事实，不承担科学解释，也不默认成为 worker 必读正文。

共享经验应保留：当前判断、适用条件、已知反例、被推翻的解释及原因、测量陷阱和真正未决的问题。经验是可修订的知识，不是上级指令；模型应允许新证据改变它，也不能用经验覆盖合同或权限。

一种足够自然的写法是：

> 当前观察只支持这一条件下的解释，换到另一条件尚未复现。先前的解释因某项对照而不再可靠。再次研究时先核对输入与测量口径；需要追查时看已有原始结果。

不要求为此生成每轮 memory、摘要索引、哈希表或追踪编号。使用人能理解的主题和直接链接即可。已有 runtime 的 commit/digest 等机器身份继续服务于恢复、版本和测量可比性，通常留在内部，不让研究者把它们搬进经验正文。

### 以疑问触发阅读，不以文件数量决定阅读

默认入口先呈现当前任务、工作状态、关键结论与反证线索。研究者有具体疑问时再进入已有主题章节；需要核验事实时再读取相应原始测量、代码或日志。这里是同一批现有文件的不同阅读深度，不是三套新文档。

已知的关键反证应与当前正面结论放在一起。只写“方法 A 有效”，把“条件 B 下失败”藏在旧实验深处，会让渐进披露变成选择性遗忘。保留反证线索不等于默认展开全部历史：读者先知道什么条件会动摇当前判断，再决定是否查原件。

这种方式不能保证未知的旧反证必然被找到。它能改善已知重要反证的可发现性；遇到新假设、不熟悉条件或结论冲突时，研究者仍需定向搜索历史。不能同时承诺不读历史、没有任何索引维护、又绝不漏证据。

### 选择性保存真正支撑判断的观察

不保存所有 scratch，也不只留下最终结论。某次观察影响了研究方向、支持或否定了主张，就应在清理临时工作树前保留足够的原件和必要条件，使之后的人能复查。临时缓存继续清理；已有日志或结果已经完整保存时直接引用，不复制一份“证据摘要”。

这项工作应融入现有研究解释或阶段结束步骤，不为每个微小尝试增加登记仪式。后续要在实际案例里确认：哪些原件本来已可靠保存，哪些观察确实因清理或交接而丢失，再决定是否修改持久化接口。

## 七、先收集哪些自然案例，如何判断是否值得改

先使用当前 ArcHa，让 DeepStack 平台中的真实疑问逐渐形成案例。下列情况是观察线索，不是预制题库、标准答案或强制实验清单；在已说明的内部授权与研究范围内使用。

| 自然出现的情况 | 重点观察 |
|---|---|
| 某项公开配置变化没有产生预期影响 | 是否追踪了实际消费该配置的路径，还是继续复述原假设 |
| 局部观察推翻了计划前提 | designer 能否当场诊断；哪些研究决策必须等下一轮；交接丢失了什么 |
| 正式结果与局部理解不一致 | 是否核对输入、条件、测量口径与版本，再修正解释 |
| 旧结论在新条件下失效 | 是否发现已有反证线索，是否更新当前经验而不抹去旧事实 |
| 尝试失败，但暴露了有价值的机制 | 现有失败反馈是否已经足够，重要原件能否在恢复后找到 |
| 需要回到一个旧候选继续研究 | 是否能利用已有证据选版；不把选版前的输入误当成已知本轮 parent |
| 跨阶段或跨 run 接续同一问题 | 是否只读必要经验与证据，还是重读完整地图、brief 和全部历史 |
| 一个规格清晰的简单任务 | 当前流程是否已很好；新流程是否反而过度探索或偏离要求 |

观察时主要回答：读了什么、为什么读；事实在哪里出现；何时改变了判断；实际方案与记录计划是否一致；哪些旧知识被正确复用或纠正；结论能否追到支持它的条件与原件。这些问题可以写在现有案例说明或成果人工区，不新增通用追踪系统。

有了具体问题后，再选择一个框架调整方向，例如减少默认历史展开、让 designer 只消费本轮材料、支持现场发现回写研究决策、改善关键原件持久化，或试验阶段内连续研究。先保留当前框架的案例与结果，再逐项比较变更后的行为；若同时更新 DeepStack 或输入，应明确这是另一个变化因素。

判断依据是解释是否更可靠、关键反证是否被看见、研究链是否更连贯、重复错误是否减少，以及简单任务是否退化。单次顺利完成或一个更短的 prompt 都不能证明架构更好。对不稳定现象做必要复查即可，不预先搭建完整评分体系。

### DeepStack 之外的构建与调优候选

首批建议保留一类机制研究任务和一类从明确需求出发的构建任务。前者观察如何获得可靠认识，后者观察能否把规格变成可运行产物，避免只用一种研究风格判断整个框架。下列顺序是下一阶段候选，不是已经安装、跑通或确认适合本机的 benchmark。

| 顺序与候选 | 有限任务范围 | 想观察的框架行为 |
|---|---|---|
| 首选构建：openTPU ACT RAM 小模块 | 以 `rtl/mem/otpu_actram.sv` 对应的功能为参考，从完整接口、时序和合法输入条件重新实现；agent 自行构建 testbench | 能否从需求提取关键行为，选择观测点，通过失败修正实现和理解，而不是照抄参考答案 |
| 后续开发：SNAX-MLIR 分配分析 | 在 `MiniMallocate` 现有单 block、函数顶层 allocation 范围内，研究限定的非逃逸 view/cast 链 alias 与 lifetime 支持；先证明当前支持边界，再决定扩展 | 能否读清已有能力、识别真实缺口，保持不支持 IR 的保守回退，并让方案与实际适用范围一致 |
| 后备调优：openTPU DMA LD/ST | 保持资源与协议条件，研究造成传输空泡的原因并改善；先限 LD/ST，避免同时接入所有流式计算路径 | 能否区分协议等待、数据依赖与实现空泡，构建对照而不预设解法，保留没有收益的发现 |

**ACT RAM 题目材料与研究者参考材料应分开。** 规划者可以用官方实现确认题目可定义，执行者的干净工作区不携带原实现、Git 历史或泄露答案的材料；应交代完整端口、读写时序、使能、冲突及合法输入语义，不能通过遗漏必要规格制造“未知”。testbench 由 agent 自己设计，本规划不预写验证器。若之后用原实现对照，需说明参考实现只是该版本的对照对象；agent 自测通过本身也不能证明符合全部规格。[ACT RAM 官方源码][opentpu-actram]

SNAX-MLIR 已有静态分配、minimalloc 和 double buffering 等能力，不把它们当成待补缺失功能。当前 `MiniMallocate` 遍历函数单 block 的顶层 allocation，统计直接 use，并专门追一层 `UnrealizedConversionCastOp`；因此可先研究限定别名链是否超出支持范围，而不是立刻做一般 CFG 数据流分析或改 minimalloc 搜索器。先走 Python/xDSL 可隔离的子路径；默认 pixi 环境包含较重的开发和工具链依赖，不以完整安装作为首个任务。[分配实现][snax-allocate]、[项目依赖][snax-project]

支持更多 IR 首先是功能成果，不能直接称为加速；即使降低内存高水位，也不自动意味着执行 cycles 减少。分别报告支持范围、分配行为和确有依据的性能变化。

DMA 已有 burst 请求预取、缓冲与成批写出，不能把“添加预取”预定成创新或收益来源。是否确有可改进空泡要由限定负载和协议观察确认；只做功能仿真或周期观察时，只报告对应行为，没有综合和时序证据就不宣称 PPA 或频率提升。[DMA 官方源码][opentpu-dma]

这些候选在 4 GB 条件下的可运行性尚未实测。先接一个独立模块及必要依赖，不运行 openTPU 默认 remote/tourney 流程，也不同时搭全部工程。工具链准备、原任务自身难度与框架缺陷分别观察；一个平台没跑通，不能直接归因于 agent 分工。

比较至少区分两件事：新实现是否满足需求，以及框架是否帮助研究和开发。参考 RTL、现有 pass 或官方模型回答前一类问题；当前 ArcHa、后续单项改动，以及必要时同模型、同材料和工具权限的直接单 agent，才有助于判断后一类问题。直接 agent 也应允许自主多轮，不把它压成一次回答来抬高框架。先收集自然案例与必要重复，再决定哪些比较值得继续。

### 保留探索自由，也说明证据能支持多强的结论

这里不提供我们自建的验证器、评价器、预置探针矩阵或隐藏打分体系。agent 自己设计实现、案例和解释，便于观察自然研究过程；但这三者来自同一执行者，不能自动构成独立证明。事后可以人工抽查关键主张、复跑已有官方测试，或对照规格和原有独立参考。缺少独立依据时，应称探索观察，不据此排名或声称框架优越。

隐藏参考实现和 Git 答案只能降低当前材料泄漏，不能证明模型训练时从未见过公开代码。源码辅助解析与严格黑盒任务应分别说明。旧题复跑也不是新的独立样本；同题比较应保持模型、工具权限、初始材料和终止标准一致，后来披露的共享经验本身就是一个干预因素，不能把额外提示带来的改善归给架构。

在现有观测下不可辨识、无法判断机制，也是正当研究结果。DeepStack 模型内部的解释不能冒充物理硬件实测；平台资格阶段先排除 OOM、依赖和执行环境问题，避免把它们混入 agent 能力判断。必要复查服务于结论可信度，不以 token 或时间预算优化为目标。

## 八、待讨论的轻量模板与只读 runtime dashboard

用户已确认把这一方向记录下来；具体模板、字段、状态和接口尚待实际案例验证。记录目标不代表现在开发 dashboard、修改框架或推送代码。

### 先分清信息职责，再决定是否需要模板

目前需要区分五类信息，但这不意味着新建五套目录或规定每类必须独立成文档：

| 信息类型 | 主要回答的问题 | 建议复用方式 |
|---|---|---|
| 任务约定 | 要解决什么、验收依据是什么、哪些范围和权限不能改 | 既有 brief、冻结合同与相关需求；执行者不反复重写任务背景 |
| 实际产物与临时材料 | 实际改了什么、产生了什么，哪些值得交付或保存 | 源码、规格、候选、既有结果位置；临时材料按价值选择性保留 |
| 实验事实与解释 | 做了什么、观察到什么、这些观察支持什么或仍无法说明什么 | 原始结果与现有分析段落分别表达；执行成功与科学解释分开 |
| 条件性团队经验 | 哪些认识值得复用、在什么条件下成立、有什么反证 | README 人工区或已有主题规格；允许修订，不复制整个实验账本 |
| runtime 运行事实 | 当前在执行什么、worker 何时开始/结束、有哪些事件、哪里缺少观测 | runtime 自动产生的事件和当前状态，由机器接口服务外部展示 |

面向人和 agent 的模板可以薄一些：任务约束、阶段接手所需信息、经验的条件性结论，给出应表达的含义即可，允许自然语言和不同任务采用不同结构。已经由合同或原件提供的信息直接引用，不要求重复填表。

**交接是一份从现有材料选择出来的当前视图，不必每轮生成 handoff 文件。** 它应让接手者明确目标、实际工作版本、已知判断与关键反证、未决问题，以及哪些材料必须读、哪些按需查；在 expert 尚未选版时只能描述默认工作状态，不能假称已知本轮 parent。视图可由现有入口和 runtime 中已知状态组成，具体表达方式待实践后确定。

### worker 的阅读文档与机器接口分开

只读 dashboard 应消费 runtime 自动提供的稳定事件与当前状态，不靠抓取 worker 临时 prose 猜状态，更不要求 worker 为 UI 另写状态报告、手动复制工具日志或维护哈希索引。先核对并复用 ArcHa 既有 observer、事件与报告能力；必要关联沿用已有 task/run/attempt。

需要保持哪些稳定状态、如何表达事件顺序和兼容性、是否提供 schema version，属于未来接口讨论项。此时不冻结字段，也不另外增加人写编号体系。研究阶段可作为面向人的展示分组，其与现有 run/attempt 的关系应根据实际流程确定，不能假设当前已经有独立阶段实体。

至少要清楚表达几种区别：

- worker 退出，不等于任务完成；退出还可能是失败或中断。
- 程序成功，不等于研究假设成立。
- 候选已生成，不等于通过验收或已经交付。
- 暂时没有事件，不等于卡死；也可能是长操作、等待或观测通道缺失。

未知状态应显示观测缺口，例如“尚无后续回执”或“此过程未采集事件”，不能从沉默推断成功、失败或模型正在做什么。

### 展示默认简洁，保留追查原件的能力

未来界面可先围绕“任务 → 研究阶段 → worker 事件与产物”展开：默认展示当前状态、最近关键变化、已有显式理由及相关产物入口；用户有疑问时再展开工具调用、结果或原始材料。展示摘要与权威原件分开，摘要不改变实验事实和任务完成语义。

这里的 worker 行为可见性指工具调用、返回结果、文件变更以及它主动提供的理由和结论；不宣称能显示模型隐藏思维，也不把缺失的解释补造成心理活动。需要解释决策时，可以让 worker 在现有交接或结论中简述依据，不要求持续写思维日志。

等真实实验中出现“当前到底处于什么状态”“这项结论依据是什么”“接手时该读哪些材料”这些具体困难，再分别补 runtime 接口、经验表达或交接模板。先把真正不清楚的地方说清楚，不预先铺设大量状态文档。

## 九、EAT 对照中保留的启发与下一步落点

EAT 的 supervisor 编写每个角色的自由文本 Prompt，普通 parser 提取后由 CLI 执行；角色的文件阅读与交付约定并非强制产物 schema。团队结果由脚本摘取最终回复等内容，再交给下一轮 supervisor，并非把所有 trace 全部自动传回。

值得保留的是明确本轮问题、交接入口、原件位置和独立正式评价的思路。按行截断、全文 notes、累积历史以及自由文本目录约定，不应被当成更成熟的语义相关性管理或文件隔离。ArcHa 已有的确定性执行、恢复和失败反馈无需为模仿 EAT 重做。[EAT 配置解析][eat-parser]、[EAT 结果汇总][eat-team]

下一步首先是把用户已有的 DeepStack 平台逐步变成可开展研究的现场：能提出一个具体问题，在已说明内部授权范围内沿接口与可用代码观察，留下足够事实，形成可修订的解释。ArcHa 的改变由这个过程中的真实障碍驱动。

当前保留的待验证方向是：让默认材料更相关，让同一问题中的推理更连续，让共享经验能被纠正，让重要原件确实活下来，同时保持 runtime 的可信执行边界和必要的独立审核。是否有效，留给实际案例判断。
