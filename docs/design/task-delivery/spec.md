## 1. 用户目标与已确认决策

正常使用过程中，用户在 `archa-map`、`archa-task` 中澄清目标、范围、完成条件和预算。进入执行后，ArcHa 自主准备、开发、验证、修复和终验，不能把普通开发待办交回用户，也不能把 `run` 停止当作任务完成。

用户已确认：

1. onboard 必须自主完成必要接入准备；不能通过留下开发阻塞来缩短自身时间。
2. 放宽开始工作的证明门槛，集中保留最终结果的真实验收要求。
3. 将 `promote` 接入 `archa-loop`：执行、终验、必要修复、再次终验形成连续流程。
4. 普通实现缺陷和证据缺失由 agent 在原授权范围与预算内修复。
5. 用户可在终验失败后明确修改验收标准，复用已有结果重审；原标准、失败事实和原始证据不得被覆盖。
6. 默认终验不自动 `--apply` 到用户分支。通过终验与应用代码分开。
7. 先改 ArcHa 源仓库并离线验证，再同步项目 runtime；本次不得修改 PIM 的现行合同、标准、实验原件或账本。
8. 不引入通用调度平台、复杂准备状态机、上下文包管理系统、通用 gate 框架和新的性能数据平台。

正常路径不需要新增用户确认；改变目标、验收含义或总预算，仍由用户决定。外部权限、不可获得的设备或预算耗尽可能导致未完成，不能承诺任何研究任务都一定成功。

## 3. 唯一用户流程

```text
map/task 澄清并确认目标、验收、范围、预算
    → onboard 自主完成必要接入准备
    → loop 完成执行准备并运行
    → promote 审核选定版本
        ├─ 通过：交付报告与版本，不自动 apply
        ├─ 可自主修复：在原预算内继续开发，再终验
        ├─ 标准含义需要改变：解释冲突，等待用户明确决定
        │    └─ 用户确认新标准：新 revision，复用已有结果重审
        └─ 用户停止／预算不足／真实外部阻塞：保留结果，如实报告未完成
```

用户要求只准备、暂停或停止时，尊重该边界，不能为了完成终验自动继续。调用 loop 代表在已有范围与预算内执行及终验的授权，不等于 apply 授权。

普通技术错误不是邀请用户参与的理由。只有确实无法自主解决的外部条件，或需要改变用户决定的事项，才返回用户。单纯一次命令失败不能直接归类为外部阻塞。

## 4. 第一阶段：缩小证明要求，保留完整准备责任

### 4.1 onboard 的完成条件

onboard 结束时应具备：

- brief 的目标、要求、范围和预算正确进入合同；没有模型自行添加的硬性验收条件。
- 当前任务的评价器、输入输出约定和必要工具已接入。若缺失，agent 在本阶段自主开发。
- 执行所必需的环境事实已知；必要时做有界探针，不要求提前完成正式研究。
- 关键接入验证已通过；未实现产品和缺少正式原件能被报告为未完成，不会被误报成功。
- 留给 loop 的是已有职责：固定执行基线、执行检查、正式运行；不是尚无人处理的评价器开发待办。

onboard 的成功仅表明可以进入执行，不表明科学结论成立。执行开关按现有 task/loop 分工处理，不在 onboard 提前启动正式实验。

### 4.2 删除默认的全套准备证明

将默认要求改为“与本次改动对应的必要验证”，删除每项任务固定开发完整负控套件、固定独立准备 reviewer、固定通用监控工具建设的要求。

- 复用未修改的已有评价器：做接入检查，不重复证明所有内部逻辑。
- 新增适配层：验证一条合法输入到输出的路径，以及本次最可能造成假通过的关键失败路径。
- 新增关键验收算法：按算法实际风险补测试；必要时进行针对性独立审阅，不等于所有任务都必须审阅。
- 研究结论和正式实验充分性：放在终验，不要求在准备阶段证明。

不设“一律只运行两个测试”的机械限制；也不要求给每项检查再生成一份存在理由报告。直接在必要日志或已有结果中说明关键判断即可。

独立准备审阅不再是通用 ready 前提。已确认任务若明确要求这一审阅，仍执行；取消用户明确要求需要用户确认。代码需同步调整 `static_check/hard_check`，不能只移除 reviewer 调用而保留依赖其回执的门禁。

### 4.3 缩小冻结与产物范围

使用当前 task、对应 component、实际 evaluator_files 和显式共享依赖确定冻结集合。不要扫描全部任务，更不要为此引入依赖图服务；优先复用现有合同路径和 glob。

保留合同、必要原始日志、现有账本和正式实验原件。状态和交接摘要引用这些权威记录，不另建内容相同的准备报告链。每次调用日志独立保存；查询结果不等于新的证据副本。

失败后修复当前缺口，尽量复用现有文件和已通过检查。无需搭建通用阶段缓存系统；至少避免“只缺审核或只记账，也重新调用完整准备 worker”。

## 5. 第二阶段：将终验与修复接入 loop

### 5.1 调用及职责

正常执行停止并选定交付版本后，loop 自动调用现有 promote 逻辑。若要求包含 review，则选择已配置的 reviewer；只需确定性检查的任务不额外强制模型审核。终验必须绑定 selected commit，不能退回冠军或 latest 文件来替代。

编排保持在现有技能与引擎职责内：技能决定如何处理具体 findings，引擎保证版本、预算、冻结合同和结果绑定。只补必要的续接接口，不新增另一个常驻通用控制器。

现有 promote 默认不带 `--apply`。loop 报告终验是否通过、选定版本、未满足要求和已有原件路径；run 的 stop_reason 不再替代完成结论。

### 5.2 终验失败的处理

| 失败类别 | 自主动作 | 结束条件 |
| --- | --- | --- |
| 实现缺陷、缺少交付文件 | 把具体失败要求反馈 expert/designer，修复后重审 | 通过，或原预算无法继续 |
| 缺少实验原件 | 在已授权范围内补真实执行与采集 | 外部资源确实不可用、预算不足或成功 |
| 评价器实现错误 | 修复实现并保留原失败；冻结变更按现有 revision/run 规则办理 | 不得降低要求或覆盖旧运行 |
| reviewer 暂时不可用、输出格式错误 | 针对审核重试或修复调用，不重做候选开发 | 可用预算及既有重试限制耗尽 |
| 标准与用户目标可能冲突 | 展示具体要求、实际结果和影响，等待用户决定 | 不自动降标；不把每次失败都升级为标准讨论 |
| 用户暂停／停止 | 保留状态并停止新增工作 | 用户重新授权恢复 |

已有 findings 足够时直接使用，不另建庞大的错误分类系统。若增加机器可读原因，仅增加实际控制流程所需的少量稳定值，并与人类说明同存于现有结果。

### 5.3 closed run 与预算

当前 closed run 不能直接恢复，因此不能只在技能里写“再次 run”。建议复用现有新 run 机制承接终验修复：显式记录来源 run、选定候选和失败 promotion，在相同 task 和原授权累计预算内继续，不创建新 task 来规避累计消耗。

该续接是已经授权的任务修复，不是用户新开研究轮次。不得覆盖原 run 的停止原因；新 run 起点必须是本次选定候选，不默认冠军。不应广泛改变所有 closed run 的恢复语义。

新 run 必须使用正确的评价器和合同基线。若候选的评价器 digest 与当前合同不匹配，应走明确的准备／新 revision 路径，不能跳过 `--base` 的一致性检查。

终验也消耗总预算。执行调度应留出实际可用的终验余量，优先利用现有预算检查与保留机制，不新增多套阶段账本。不足以完成终验时报告“未完成终验”，不能因 run 正常结束而报告成功。用量未知时不猜测为零；程序计量问题由框架修复，不能要求每个项目重新开发监控。

对于无变化的重复失败，不无限重审；须有具体修复、可重试的外部状态变化或用户确认的标准修订，才继续。复用已有重试限制和总预算，无需增加任意的新循环上限配置。

## 6. 第三阶段：用户修改标准后复用结果重审

### 6.1 适用语义

用户有权改变交付要求，agent 无权自行降低要求。确认必须明确指出修改了哪项要求，以及新要求是什么。不能以 reviewer 建议、用户沉默或一次失败代替确认。

案例：用户要求探索 PIM emulator 的硬件结构、容量、带宽与执行流程，覆盖 FP16、W4A8。覆盖两种模式不自动意味着数值必须与参考实现完全对齐。用户可以将数值对齐改为诊断信息，但依赖数值正确性的硬件推断仍可能未证实，必须保留条件和限制。

本方案只实现这项能力，不替用户修改 PIM 当前标准。

### 6.2 最小数据与接口设计

继续使用 task 的 revision 保存新标准。原执行 run 及其冻结合同保持不变；新标准是本次审核所依据的合同，不伪装成原实验当时使用的合同。

在现有 promotion report／ledger 中记录必要关联：来源 run、选定 commit、新验收 revision/digest、用户确认的标准变更依据、复用的原件或评价引用。字段名由实现与现有模型统一；不得另建平行的标准版本数据库。

建议为 promote 增加显式来源 run 的能力，并明确区分执行合同与本次验收合同。CLI 名称以实现时已有接口为准，文档示意不得当作现成命令。跨 revision 重审必须由显式动作进入，不能仅删除现有 digest 比较使任意合同都能审核任意 run。

只改验收标准时不需要新 designer 候选、不需要重新 onboard 整个项目，也不必新建虚假执行 run。沿用原 task 的累计授权预算，独立记录此次审核消耗。

### 6.3 三种变更分别处理

1. **只改验收阈值、必需性或审核说明**：候选与评价器不变。复用仍适用的测量／原件，用新条件重新判定；旧结论不能直接复用为新结论。
2. **增加／改变所需证据**：只补缺失的验证或实验；若涉及新执行行为，确认其仍在授权范围内。
3. **改变评价器实现或目标范围**：不再是纯标准重审。需要新的冻结评价实现／revision；旧测量不得冒充新评价器输出，目标变化需要用户确认。

纯标准修改必须限制在验收相关字段。若同时改变 editable、设备行为、数据来源等执行语义，不可通过重审入口静默放行。

当前证据缓存键包含 task digest，直接沿用会使标准变化触发全面重测。实现时区分“测量是否适用”与“判定是否适用”：候选、评价代码、实际输入、环境及时间有效性决定测量复用；验收 revision 决定新判定。只使用已有可验证信息，无法确认适用性时定向重测，不先建设通用缓存平台。

历史失败报告保持不可变。新报告说明“按新标准通过”，同时保留精度偏差等已观察限制。不得重写旧 report 的失败为通过。

### 6.4 diagnostic 与硬性 gate 的实际耦合

当前 promote 会将任意已运行 gate 的非 passed 状态作为阻断。因此，仅把 requirement 改成非必需，可能仍被原 gate 的总失败阻断。

实现必须检查这条链：用户修订的要求 → requirement 判定 → gate 输出 → promotion 汇总。对于诊断信息，优先让评价器输出观察指标，由合同决定其是否构成失败；不要在框架里写 PIM／精度特例。

如果现有 gate 将多个必需与诊断条件混在一起，应做最小拆分，或使用已有模型表达必要性。确需增加字段时只增加一种明确语义，并保证默认兼容旧合同的硬性 gate；不得默默把所有失败降成 warning。旧评价器需要修改时，按上一节第 3 类办理。

## 8. 实施顺序与交付范围

### 步骤 A：核对新服务器基线

- 检查仓库指令、Git 状态、实际版本和当前测试配置。
- 定向核对第 2 节列出的行为，识别已经合入的修复及未提交补丁。
- 在独立分支开发，保留无关修改；不要批量覆盖工作区或直接套用旧服务器全部差异。
- 先运行相关既有测试建立基线，记录既有失败，不为本方案启动真实 PIM 实验。

### 步骤 B：精简 onboard

先完成准备门槛与 task 范围调整，更新技能／指南。验证必要接入可完成、真正的接入错误仍阻断、无关任务修改不触发当前任务重验。保持原有用户明确审阅要求可表达。

### 步骤 C：闭合 loop

接入自动 promote，打通选定候选续接修复和共享预算；不要通过重置 run 或将 target_met 当完成来绕过终验。区分停止、暂停、预算耗尽和可修复缺陷。

### 步骤 D：标准修订重审

显式绑定旧执行与新标准，先支持纯验收变更，再覆盖需要补证据的情况。验证不变的候选无需重新开发、不适用的证据不会被误用、硬性 gate 与诊断信息不会产生矛盾判定。

### 步骤 E：集成验收与移交

完成下表回归，运行仓库规定的相关质量检查。必要时做一次有界真实模型 smoke，但必须有明确预算和可用环境；离线通过不能宣称真实模型或手机实验已验证。

交付代码、测试和一份简短实现结果说明即可；可直接在本文末尾补实际提交、检查结果、限制及使用示例，不新增多份相同内容的报告。验证通过后再讨论目标项目 runtime 同步及 PIM 具体标准修订。

## 9. 回归验收矩阵

这些是行为测试要求，不要求每条单独一个测试文件。优先扩展 `test_research_loop.py`、`test_engine.py` 和现有 preparation／promotion 测试；共享临时项目夹具，避免复制整套项目。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常准备 | 必要评价器接入成功，默认不额外调用准备 reviewer；无需重复证明已有工具 |
| 准备缺少适配器 | agent 完成开发与必要验证，不把普通待办交给用户 |
| 任务明确要求准备审核 | 仍进行审核，不能因默认简化而跳过确认要求 |
| 缺少正式研究产物 | 不伪造成功；无 objective 的未完成基线仍能进入开发 |
| 真实工具／输入契约故障 | 不能误报为产品尚未实现；自主修复或报告真实外部条件 |
| 无关 task 文件变化 | 不使当前任务准备凭证失效；共享评价依赖变化仍会失效 |
| 正常开发结束 | 自动终验正确 selected commit，通过后交付，不自动 apply |
| 一次可修复终验失败 | 将具体 findings 反馈给修复轮，保留原失败，之后重审成功 |
| closed run 修复续接 | 从选定候选继续，不默认冠军；沿用 task 总预算，旧 run 不被改写 |
| 用户暂停或停止 | 不因自动终验／修复而恢复工作 |
| 预算耗尽或用量未知 | 不新增未授权派发、不重置额度；未终验则明确未完成 |
| 只缺 reviewer 回执 | 重试审核，不重启 designer，不重复仍适用的正式测量 |
| 用户修改标准 | 新 revision 明确关联旧 run／候选，旧失败保留，按新标准重审 |
| 没有用户确认的降标 | 不可进入标准修订路径 |
| 仅验收条件变化 | 仍适用的测量复用；重新生成判定，不制造新实验记录 |
| 评价器／输入变化 | 不复用不适用测量；只补受影响检查或执行 |
| 诊断性精度偏差 | 按用户新标准可不阻断；报告仍显示偏差及受影响的推断限制 |
| 硬性正确性要求失败 | 仍不能通过，不能用 diagnostic 机制普遍绕过必需验收 |
| 两个不同 run 的结果 | 显式选来源，不能由于 latest 变化审核错候选 |
| 旧合同与旧报告 | 保持可读且默认语义不变，不批量迁移或改写历史 |

离线测试需检查模型角色调用次数：不该唤醒时为零，只缺审核时没有开发调用。不要用真实模型成本作为唯一回归判据。若技能是外层编排入口，除了单元测试还需验证其实际命令消费顺序；Python 测试通过不自动证明技能执行正确。

## 10. 完成标准与不做事项

本次改造完成须同时满足：

1. 正常任务从确认后的准备到终验可自主推进，不向用户交回可修复开发待办。
2. onboard 不再默认建设全套证明工程，但必要接入验证没有消失。
3. loop 的交付结论来自终验，不来自 run 停止状态。
4. 用户可明确修改标准并对同一候选重审，历史事实保留，预算连续。
5. 没有新增重复账本、重复证据包、通用阶段编排框架或 PIM 专属框架规则。
6. 相关离线回归通过，真实模型验证范围如实标注，源代码与技能／文档一致。

不要求证明具体 token 节省比例；不为性能验证重跑已接受的 PIM onboard；不修改用户既有实验或全局环境；不默认部署到外部项目；不自动 push、merge 或 apply。




## 11. 实施结果（2026-10-28）

本节记录本次实际实施；前文是原始输入方案。用户后续要求独立 tickets，因此增加 tickets.md 并按顺序提交。

- D1：默认必要接入检查，preparation_review=true 保留明确准备审核；当前任务/component/evaluator_files 冻结，独立审核重试复用摘要相同的文件和证据。
- D2：run --deliver 自动终验明确来源；repair-promotion 验证已登记报告和 SHA-256，从 selected commit 建新 run，记录来源与 findings，保留旧 run。loop 技能消费 findings 自主修复；reviewer 故障仅重试 promote。
- D3：显式 source-run + 新 revision + 用户确认文件进入纯标准重审；执行合同与验收合同分别记录。同候选、评价器、工具链、环境的已有测量可复用，判定重新生成。requirement.required 默认 true；false 的诊断要求及其独占 gates 不阻断，硬性要求、未声明 gates 和基础设施失败保持阻断。
- D4：整合 task 累计预算、未知用量、用户控制、报告绑定、准备审核复用、技能说明和 CLI 离线行为验证。

### 新接口

```sh
# 默认准备；仅明确要求独立准备审阅的合同设置 preparation_review: true
python -m opc onboard -p PROJECT --task TASK --max-tokens TOKENS --max-wall-seconds SECONDS --prior-tokens HOST_TOKENS --prior-wall-seconds HOST_SECONDS

# 正常执行与终验，默认不 apply
python -m opc run -p PROJECT --task TASK --revision r0001 --deliver

# 已登记终验失败的范围内修复；旧 run、旧报告不变
python -m opc run -p PROJECT --task TASK --revision r0001 --repair-promotion PATH_TO_REPORT_JSON --deliver

# 仅重试审核，不重新开发；仍适用的测量可复用
python -m opc promote -p PROJECT --task TASK --revision r0001 --source-run RUN --review codex

# 用户明确修订标准后，同候选重审
python -m opc promote -p PROJECT --task TASK --revision r0002 --source-run RUN --standards-confirmation confirmation.json
```

确认文件必须显式匹配来源、旧新 revision 和实际变更。changes 只列发生变化的 requirements / acceptance，old/new 使用对应字段的完整原值，不接受仅写“同意降标”。例如仅 requirements 变化：

```json
{
  "confirmed_by": "user",
  "source_run": "run-...",
  "from_revision": "r0001",
  "to_revision": "r0002",
  "changes": {
    "requirements": {
      "old": [{"id":"R1","text":"阈值要求","check":{"metric":"error","op":"<=","value":0}}],
      "new": [{"id":"R1","text":"诊断误差","check":{"metric":"error","op":"<=","value":0},"required":false}]
    }
  }
}
```

文件是用户决定的显式记录，不能由模型自行生成用户同意。代码校验内容对应性，不提供用户身份认证。禁止通过此入口改变目标、预算、执行字段、objective 或 component/evaluator；这类变化走新的冻结合同/执行路径。
