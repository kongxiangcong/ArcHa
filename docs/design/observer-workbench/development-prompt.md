## 目标与优先级

我已确定：**首版仅观察，不做控制。保留原型的视觉和浏览联动，优先复用开源组件，用稳定观察接口隔离 ArcHa 的版本变化。**

完成后，我应能从研究任务或直接任务进入某个 run，看到五阶段记录、每轮专家方案和开发实际成果、已有结论与缺口，点击产物查看关键内容和原文，并下钻到一次 agent 调用。

优先级依次为：只读与事实准确 → 保留原型信息结构 → 贯通真实格式的数据读取 → 复用组件与可维护接口 → 必要视觉细节。来源没有记录的信息可以未知；不能为了填满界面改变 ArcHa 工作流。

## 开工步骤

1. 检查 Git 状态、分支与项目约定，保留用户已有修改。核对远端 main；在独立开发分支（建议 `codex/observer-workbench`）工作。已有同任务分支则继续，不重置、不强推、不把其他未提交改动混入本任务。
2. 完整阅读 spec 与原型，再对照当前代码核实来源路径、表结构、冻结合同、brief 关联及调用日志。源码位置变了就在实际位置实现；不能自动改用户部署目录或升级 `.opc/runtime`。
3. 在 `docs/design/observer-workbench/tickets.md` 创建本任务唯一工单清单。约 5–7 张票即可，按实际依赖拆分。每票包含目标、范围、前置、对应 spec 要求与 A01–A16 验收、涉及位置、验证方式、状态。
4. 核对全部决定和验收场景都被工单覆盖，然后**直接逐票实施，不等待第二次确认**。本次任务授权包括 tickets 梳理和后续开发，不能只返回计划、第一张票或新的静态样板。

## 必须保持的实现边界

- 前后端都不提供启动、暂停、停止、续跑、重试、审批、promote/apply、改目标、编辑合同或工具执行入口；不留禁用控制按钮、空控制路由或未来控制 SDK。
- 原型中的阶段和轮次只是观察导航。保留顶部任务、三种状态、完成条件、左侧轮次/角色/产物、右侧要点/原文及窄屏单列；不重新设计成大型后台或总览仪表盘。
- 只有地图任务依赖使用 React Flow + Dagre；Markdown 使用 react-markdown + remark-gfm；需要排序筛选的表格复用 TanStack Table；调用内容使用 assistant-ui 只读 primitives。前端用一个 React/TypeScript/Vite 应用，原型 CSS 就地迁移。
- assistant-ui 首选已核查的只读 Provider 和 MessagePrimitive.Parts。不要使用弃用的 makeAssistantToolUI，不为历史消息建立可执行聊天运行时，不增加 onNew、工具 execute 或审批回调。
- 数据读取集中在一个薄 ArcHa adapter，前端只消费 spec 的观察 DTO/API。保留源状态、稳定 ID、来源定位和未知字段。测试/演示把来源根指向 fixture，复用同一 adapter，不再写第二套解析器，不建设通用插件、消息总线、第二套数据库或工作流引擎。
- 不构造当前 Engine/Ledger 查询对象，不轮询 `opc status/report/check`，不执行 reconcile、promote 或恢复。它们可能写入或实际执行。只读打开已有 SQLite，正确处理 WAL、短事务、半行日志和文件替换；允许 SQLite 正常读协调，不为物理辅助文件变化另造快照系统。被新调用复用的日志不能回填给旧调用。
- 不改执行语义，不增加埋点、heartbeat、agent、reviewer、摘要调用、评价器和强制产物。缺实时活动显示未确认，缺结论显示未记录。
- 历史 run 按自身 frozen/revision/digest 解读；不能拿最新 task/brief 覆盖旧目标。preparation 不强套正式 revision，地图勾选不代表任务完成。
- 要求验证方式与结果分开，候选保存与任务通过分开，run 结束与终验通过分开。未知成本不填 0，不制造评分、完成百分比、ETA 或假心跳。
- 服务只提供读取接口，默认 loopback；artifact 用登记 ID 读取允许范围内的文件，避免任意路径访问，Markdown/HTML 等内容不执行脚本。
- FastAPI/Uvicorn 通过 optional extra 安装，核心 CLI 不依赖观察模块。构建后的前端由同一个 Python 服务托管；不引入云平台、模型密钥和常驻 Node 服务。
- 不引入本 spec 推迟的 Recharts、react-o11y、Phoenix、AgentOps、OTel、CopilotKit/AG-UI。没有真实需求时不扩展候选清单。

## 工单实施方式

- 状态使用 `todo/in_progress/blocked/resolved`。开工设 in_progress，满足对应验收后设 resolved，记录实际实现、检查命令/结果和限制；不要提前标完成。
- 按依赖顺序逐票推进。每票完成必要实现与有意义的验证后再进入下一票；可以委派独立核查和审查，避免并行改同一文件。
- 按仓库约定提交本任务改动，提交范围明确，不夹带他人修改。仅为观察器调整普通代码组织时自行判断，不重复索要常规实现许可。
- 不为每票另建报告、计划或测试汇报文档。状态与验证记录统一写 tickets，用户使用说明写现有合适入口。
- 验证失败就在当前票修复；遇到真实外部阻塞记录具体原因并继续其他可执行工作。不能用增加框架层、削弱 spec 或伪造通过来解除阻塞。
- 不处理旧 task-completion 的真实模型 pilot 或旧 benchmark 工单，不删除用户数据，也不为本看板重新运行昂贵的业务任务。

## 验证方式

1. 自行构造 spec §10 的小型源格式 fixture：地图/直接任务、brief、两版合同、SQLite、至少两轮记录、Codex/DSH 日志、补丁和终验报告正反例。通过真实 adapter 读取，不能只做硬编码假数据前端。
2. 用普通 SQLite/文件写入器追加记录，验证刷新、半行日志、截断/替换、缺失/不兼容、当前状态与历史回看。此过程不用模型或 API key。
3. 核对 A01–A16，重点包括：只读无副作用、历史 revision 不串证据、未知成本、调用内容不串、浏览/重挂载工具卡绝不执行工具、合法外置产物与越界拒绝。
4. 执行前端类型检查与构建、后端新增及受影响测试、一次实际浏览器端到端浏览链，并检查 1440×900 和 390×844 截图。使用已有浏览器/测试工具优先；依赖需要安装时放隔离环境，不改变核心产品需求来适应当前机器。
5. 完成干净 checkout 的安装/构建/启动检查，提供 `python -m opc.observer --demo` 和 `python -m opc.observer --project <path>` 的实际可用命令。检查原 CLI 在未安装 observer extra 时仍可用。
6. 最后做相关回归与 `git diff --check`。不因机械追求测试数量扩展矩阵，不运行与本任务无关的模型/设备试验。
7. 有现成真实运行包时可只读补验。没有真实运行包仍完成离线验收，明确“已验证当前格式 fixture，未验证用户实际部署”，不能把示例数据说成真实 run，也不能要求我提供素材后才开始。

## 完成定义与最终交付

任务完成时应同时具备：

- spec 范围内的可运行观察服务、前端和离线演示；
- 唯一 `tickets.md`，所有可完成项已有对应验收，剩余阻塞逐项说明；
- 实际版本/依赖锁定、源格式与观察接口的边界、安装启动和升级适配说明；
- 关键浏览交互、两种视口、只读性与历史证据归属的验证结果；
- 清晰区分源码核查、fixture 验证、实际浏览器验证和真实用户运行包验证。

最终回复给出主要实现、每张票状态、可复制运行命令、实际验证与限制，以及本地分支/提交信息。远端推送和 PR 操作遵循当前会话已有授权；没有该授权时完成并交付本地工作，不影响代码和验收收口。不要自动合并或部署公开服务。
