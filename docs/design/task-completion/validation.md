# 单任务工程交付验证

日期：2026-10-27。状态：方案已确认、素材已构建并自检；**框架离线实现已执行；真实模型对照因 Codex 运行目录只读而阻塞，结果见 tickets T6**。
依据：[spec](spec.md)、[tickets](tickets.md)。本文件取代此次改造继续扩建/运行旧 benchmark 的计划。

## 1. 要证明什么

分开回答两个问题：

- **案例可行性**：ArcHa 能否从一个未完成但可运行的基线，交付符合明确要求的程序，并正确处理验收、证据和停止？
- **框架增益**：面对同一任务，与直接 Codex 相比，交付质量、人工介入和准备到交付的成本是否值得？

一次成功只支持这个案例；一组 A/B 只是先导对照，不能证明稳定胜率、一般工程能力或研究创新。不要以外层轮数多作为成功，也不要为制造多轮而拆碎任务、临时增加需求或故意注入执行错误。恢复、预算与错误分支由 spec A1–A12 的自动测试覆盖。

本例是**人工构建、具有真实工程语义的开发任务**，不是已核实的外部项目工单。它适合先检查可行性，后续外推到成熟仓库仍需新的证据。当前无需用户提供源码、日志、芯片数据或验收样本。

## 2. 唯一任务与现成素材

任务：给串行描述符执行器增加有限深度 DMA 队列、背压及计算重叠；交付代码、测试和使用说明。它没有需要优化的数值 objective，周期值是正确性输出。

素材目录：[tools/tests/fixtures/dma_backpressure](../../../tools/tests/fixtures/dma_backpressure/)。这些是测试输入，不加入 ArcHa 运行时，不引入另一个 benchmark 平台。

| 文件 | 用途 | 开发 agent 可见 |
| --- | --- | --- |
| [TASK.md](../../../tools/tests/fixtures/dma_backpressure/TASK.md) | 完整需求、接口、边界与手算时序 | 是，两组相同 |
| [starter/dma_model.py](../../../tools/tests/fixtures/dma_backpressure/starter/dma_model.py) | 能运行的串行起始实现 | 是，两组相同 |
| [starter/public_checks.py](../../../tools/tests/fixtures/dma_backpressure/starter/public_checks.py) | 四个公开需求检查 | 是，冻结原件；允许另加开发测试 |
| [starter/example.json](../../../tools/tests/fixtures/dma_backpressure/starter/example.json) | 可以直接执行的 JSON 输入 | 是，两组相同 |
| [acceptance.py](../../../tools/tests/fixtures/dma_backpressure/acceptance.py) | 固定种子数据生成、逐周期参考计算、外置检查 | 否，终验操作者持有 |
| [test_dma_task_materials.py](../../../tools/tests/test_dma_task_materials.py) | 素材正向控制、手算锚点、错误实现探针 | 否，终验操作者持有 |

只把 starter 内文件和 TASK.md 复制到两个独立任务仓库。不要将整个 ArcHa 源码、acceptance.py、素材自检、以前的解答或另一组候选复制给开发 agents。ArcHa 组另安装当前待验证 runtime。两组都可调用同一个冻结公开检查，终验参考实现和额外输入在两组产物锁定后才使用。

该分离防止普通开发流程泄露答案，不声称同一 OS 用户下构成恶意 agent 安全隔离。若模型主动读取了参考实现或另一组解答，本次对照无效；如实记录，不保留其结果冒充独立完成。

## 3. 原始输入怎样构建

全部数据由标准库生成，可离线复现：

- 10 个定向合法输入：深度 1/2、依赖、开始时取数、同周期完成/发射顺序、队首 release 阻塞、空任务、地址重叠、带宽向上取整和计算单元占用。
- 两个固定种子 `1701`、`4301`，每个生成 32 个合法输入：48 字节内存、1–18 条描述符，改变深度、带宽、setup、release、依赖和地址区间。
- 8 个非法输入：零队列深度、布尔带宽、负 setup、零长度、越界、重复 ID、向前依赖、非法字节。
- 合计 **82 个函数输入**，另外执行一次有效 CLI 和一次非法 CLI 检查。不存在厂商实测数据；不用于校准硬件延迟。

在 ArcHa 仓库根目录运行：

```bash
python -m unittest discover -s tools/tests -p test_dma_task_materials.py -v
python tools/tests/fixtures/dma_backpressure/acceptance.py generate .tmp/dma-validation/inputs.json
python tools/tests/fixtures/dma_backpressure/acceptance.py evaluate --candidate tools/tests/fixtures/dma_backpressure/starter/dma_model.py --data .tmp/dma-validation/inputs.json --output .tmp/dma-validation/baseline-acceptance.json
```

第三条对起始版本**应该返回 1**，因为它没有实现目标功能；不能为让 preflight 通过而改评价器或将功能失败改成环境错误。`generate` 产生输入原件；固定源码版本与种子即可重建。运行后记录该输入文件与验收器的 SHA-256，两个候选使用同一份，运行中不改种子或参考答案。

参考计算使用易审查的逐周期推进；目标实现不限定算法。除与参考计算逐字段比较，还用手算时序锚点验证参考计算本身、整体平移 release 的不变量检验生成输入，并确认六种错误实现均被拒绝。不能仅靠“参考实现对自身比较通过”证明验收器正确。

## 4. 准备两个独立起点

用普通文件复制和 Git 即可，不开发新的试验调度器。工作目录用本地 `.tmp/` 或外置目录，原始模型日志和生成仓库不提交主仓库。

1. 从 starter 与 TASK.md 创建一个干净 Git 任务基线；检查 `python dma_model.py example.json` 能运行，`python public_checks.py` 有预期功能失败。
2. 将同一基线复制为 `direct` 和 `archa` 两个独立仓库；源文件/需求/公开测试的内容摘要相同。
3. 抽签决定先后执行顺序，顺序记入已有的本票完成记录。每组使用新的模型会话，不继承本轮素材构建上下文；不提供实现路径、参考代码或人工 tickets。
4. 仅 ArcHa 组按正常流程初始化 runtime、形成简报、onboard、check/preflight、run 和终验。准备动作也计成本；不得在计时前人工完成 ArcHa 接入再与直接组比较。
5. 两组 TASK.md、public_checks.py 都视为冻结验收依据，开发测试可以新增。ArcHa 合同应为 objective none；不允许运行者手改计划、补丁或伪造指标去“帮框架跑通”。

共同的依赖准备、素材自检和起点复制属于共享准备，单列一次；组内的读需求、接入、模型调用、工具执行、公开验证、修复和收尾均计入该组。

## 5. 默认执行配置与同等边界

为使后续开发无需再追问输入，默认采用当前仓库 `opc/scaffold/workers.json` 中已有配置：**gpt-6.1-sol / medium**。直接 Codex、ArcHa 的 onboard/expert/designer 和最终 reviewer 均使用该模型/强度。若执行时此配置不可用，停止真实对照并报告，不能只给一组换模型或静默改配置。

| 项目 | 默认约定 |
| --- | --- |
| 平台 | 同一台 CPU Linux 主机；Python 3.10+；记录实际版本；无 GPU/厂商工具 |
| 模型接入 | 现有已登录 Codex CLI；记录实际 CLI 版本与启动参数，不在任务内新建 API key |
| 每组开发预算 | 端到端 30 分钟、累计 input+output 2,000,000 token；先到者停止 |
| ArcHa attempt 边界 | 最多 12 次；只作预算约束，不要求跑满；角色总 token 共用上述上限 |
| 最终独立验收 | 各候选同一外置脚本；各一个全新 reviewer 会话，单独上限 10 分钟 / 500,000 token，并归入该组总成本 |
| 执行次数 | 首先仅一组 paired pilot，不自动重跑或开展参数/模型搜索 |
| 联网与依赖 | 开发任务无需联网；双方一致禁止寻找已完成答案、读取外置参考或另一组成果；模型服务连接不受此任务材料限制 |

预算是调用边界上的停止约束；若 CLI 无实时 token 中断，返回后发现超限，按实际值报告为超预算，不称其硬上限已被保证。直接组也必须记录实际使用量；无法取得某项统计就标未知，不能按 0 处理。缓存 token 若可取得单列，不由总 token 推算金额。

ArcHa 按合同触发的内部 reviewer 若存在，计入它自己的开发预算；两组在终点锁定后的共同外置验收各执行一次，不把内部审阅成本藏到共享准备中。

模型调用不可用不妨碍 T1–T6 的离线实现与测试；但真实任务验收保持 `not_run/blocked`，不能因此把整体验收标为已完成。不要要求用户补材料，也不要虚构运行结果。

## 6. 两组执行指令

以下是交给隔离开发会话的完整任务指令。除执行方式外，两组看到相同产品目标、完成条件、边界和预算。不要把 ArcHa 改造 spec/tickets 或本文件的参考实现位置传入这些会话。

**直接 Codex 组：**

> 阅读当前仓库的 TASK.md，从现有串行实现出发完成全部需求。你可以自主调查、规划、实现、增加开发测试、调试和撰写 README。保留函数与 CLI，运行公开检查并交付代码差异与真实验证结果。TASK.md 与 public_checks.py 不可修改；不查找外部答案、不读取其他工作目录、不使用 ArcHa。允许一次会话内连续完成工作，无需向用户询问常规实现选择。使用 gpt-6.1-sol / medium，累计预算为 30 分钟和 2,000,000 input+output token。完成即停止，未完成如实列缺口；不得为了通过验收改需求。

**ArcHa 组：**

> 阅读当前仓库的 TASK.md，使用已安装的当前 ArcHa 正常入口，形成必要简报并 onboard、check/preflight、run、终验，完成同一产品需求。遵守 objective none，不构造进展分数；冻结 TASK.md 与 public_checks.py，允许新增开发测试。由框架的 expert/designer 自主选择路线和工作粒度，不在框架外替它实现产品、补写结论或手改候选。遇到框架错误保留现场，不临时修框架或反复重开 run 直到成功。各角色均为 gpt-6.1-sol / medium，接入到交付共用 30 分钟和 2,000,000 input+output token，最多 12 次 attempt。完成即停止，未完成如实列缺口；不读取外部参考实现或其他组目录。

最终独立 reviewer 不接受“编译成功/所有公开测试通过”作为唯一完成证明。由操作者在两组提交锁定后统一执行下一节，不由开发会话自行声称独立审阅已通过。

## 7. 终验、盲审与记录

1. 锁定两组终点 commit，并先检查 TASK.md/公开检查未被改动、范围合法。未完成也锁定最后实际成果，不补造完成版本。
2. 对每份终点运行外置 `acceptance.py evaluate`。比较全量事件、最终 memory、checksums、total_cycles、输入未变和 CLI 契约。正常任务应全部通过，不把通过比例当优化目标。
3. 将候选随机标为 X/Y；每位全新 reviewer 只得到 TASK、匿名代码差异、实际终验结果和使用说明，不告知组别、成本和轮数。reviewer 核查机制、README、适用边界及是否绕过验收；分别记录结论后才揭盲。去除传给 reviewer 的 `.opc` 和分支名称线索，不改候选实际测试代码。代码风格仍可能泄露组别，故称尽力盲审，不声称绝对双盲。
4. 外置输入在两组终点锁定前不反馈给任何一组。若终验失败，首次试验记失败；后续修复另记，不回写首次结果、不删失败运行。不得一边看 holdout 错误一边重跑直到首次结果变绿。
5. 产品合格需正确性、CLI、使用说明、机制边界同时满足。自动检查不能证明全部需求时，保留 review 缺口；失败数不替代需求判断。

## 8. 当前已验证与后续交接

2026-10-27 在当前 Linux / Python 3.12 环境执行：

- 82 个输入已实际生成；外置基线验收拒绝，记录 57 个失败条目（含 CLI 检查），不把它们转成任务 objective。
- 参考正向控制只在临时 examiner 目录生成，未作为任务解答交付给开发 agents。
- 未实施 T1–T6、未执行任何真实模型组、未测得框架性能收益。当前无 pytest，素材使用 unittest 完成检查；这不等于 ArcHa 全套回归已通过。
