# 合同与模板 v0.2：项目接入和需求追踪

日期：2026-10-22。新增能力是接入配置、基线与跨工件追踪。保留[原v0.1模型](models.py)、schema、样本及历史运行；本版本不是自动迁移，也不是已上线的鉴权服务。

## 1. 从 GSD 采用什么

参考 `open-gsd/gsd-core@812ddb5feb357ebf702b7f48c3e915a8ce4da384`（package 1.18.0，MIT）的 PROJECT/REQUIREMENTS/CONTEXT/PLAN/SUMMARY/VERIFICATION 模板及 coverage、onboard、fingerprint代码。[逐项源码依据](../docs/research/gsd-contracts.md)

我们采用结构与校验思想，中文模板为本项目重新编写，没有整份搬运其模板或引擎。模板数量并非质量指标；最小接入只需项目说明、需求与机器配置，计划/总结/审核随实际任务生成。

| v0.1 缺口 | v0.2 改动 | 能回答的问题 |
| --- | --- | --- |
| 任务不知道所属项目 | ProjectConfig、ComponentConfig、project/component ID | 工作流到底接在哪个项目/组件？ |
| 只有需求字符串 | 稳定requirement_id、current/target、成功条件和禁止事项 | 这项改动满足哪条需求，从什么状态变到什么状态？ |
| 材料中决定和猜测混杂 | locked / delegated / deferred / canonical_refs | 哪些已定，哪些agent可以自主决定，哪些暂不做？ |
| 有文件就容易算完成 | 可观察行为、预期产物、关键连接must_haves | 文件是否存在、真实行为是否发生、模块是否真的连通？ |
| 总体pass掩盖缺项 | 按REQ的coverage、verified_check_ids、gaps | 哪项测过，哪项只存在但尚未验证？ |
| 只记录收益 | deviations / provides / affects | 有没有偏离计划，影响哪些依赖和接口？ |
| 接续靠聊天记忆 | STATE/HANDOFF带run、事件游标、活job、review摘要 | 重启后应先对账什么？ |

不继承GSD的固定phase/wave顺序、自动commit/ship、diff字符数估token或无指纹报告的mtime降级放行。需求可以跨任务；同一任务内的必需检查不能因文件存在或自报pass而省略。

## 2. 可执行模型

[models_v02.py](models_v02.py)新增六类schema：

- `ProjectConfig`：稳定project_id、组件列表、协议版本、adapter和store别名；未知adapter不能启用执行。
- `ComponentConfig`：源码/可改/冻结相对路径、命令argv/cwd/timeout、输入引用；draft和configured区分。
- `TaskSpecV02`：保留目标/范围/验收/预算/权限，增加项目、基线、REQ、上下文、must_haves、精确依赖。
- `ExperimentPlanV02`：绑定project/task/run/attempt，声明需求、修改/删除路径、预期产物ID、假设和证伪。
- `SubmissionV02`：冻结主张与原件、`artifact_bindings`把预期产物ID对应到具体ArtifactRef（或明确missing及原因）、逐项coverage、偏离、提供/影响接口。
- `ReviewDecisionV02`：绑定固定manifest、双轴、独立coverage与gap；不能凭空接受缺失证据。

v0.1 的 `DecisionRequest` 与 `JobRecord` 暂保留原schema，生产adapter必须在权威记录中绑定project/run，不能跨项目只用task_id寻址。它们的v0.2统一升级与HTTP服务尚未实现，不能声称本轮覆盖了全部生产接口。

```powershell
python contracts/build_examples_v02.py
python contracts/validate_v02.py
```

示例在 [examples/v0.2/](examples/v0.2/)，schema在 [schemas/v0.2/](schemas/v0.2/)。样本有意保持draft/blocked：零摘要和template来源为占位，结构合法不表示证据真实或可派发。

## 3. 一条完整追踪链

```text
req-gemv-001（需求：候选必须正确执行）
  → TaskSpec.must_haves
      check-exact-output（可观察正确性）
      kernel / runner（预期产物）
      link-runner-kernel（真实调用连接）
  → plan.requirement_ids + expected_artifact_ids
  → submission.artifact_bindings → artifacts + coverage
  → review.coverage.verified_check_ids + evidence
  → 接纳服务核实身份、内容、硬门、预算与当前版本
```

即使kernel与runner两个文件都存在、单独功能测试通过，未验证runner是否实际执行这个kernel时仍不能把该REQ写成pass。这尤其适用于“编译→模拟器”和“模拟器请求→DRAM完成”的跨模块链路。

机器coverage状态：`pass / fail / partial / unverified / needs_human`。“文件存在”“已声明连接”“行为尚未测”是观察事实或限制，不等同pass。需要人判断的项显式保留；其余缺证据优先派发补证，不机械地要求用户处理每个未知。

当前严格规则：一次Review推荐accept时，其列出的coverage必须全部pass、两轴pass、无gap；conditional只允许在合同预先约定的条件内得出结论，不允许放宽必需检查。`priority=should`用于排程；未完成的项需显式在后续版本移出当前验收范围或保持partial，不能静默跳过。

## 4. 本轮落实的校验与边界

模型和 `check_bundle()`检查：

1. ID、有限值、未知字段与明显相对路径穿越；禁启未配置项目。
2. REQ唯一，must-have引用存在，每个REQ至少有行为/连接检查，关键连接两端产物存在。
3. dirty/非Git基线必须有明确快照manifest；干净commit路线必须有具体commit。
4. pass必须有非空证据、非空check IDs且没有待定人判断。
5. bundle中project/task/revision/hash/run/plan/attempt/submission匹配。
6. coverage精确枚举任务REQ一次，不能漏项或重复充数；REQ pass需要所有预先声明的行为及连接check。
7. 计划的产物ID在提交中必须显式标present/missing；present引用须在提交原件列表中。REQ pass需要其必需产物均有具体引用，不能用总体报告替代kernel/runner等交付物。missing作为失败证据保留，不能伪造空原件补齐。

**未在这些模型中实现：**源文件真实性、证据hash重算、实际command执行、reviewer身份鉴权、artifact store隔离、路径glob的完整授权判定、预算、live job恢复。完整运行服务仍需做这些检查，`check_bundle()==[]` 不产生accepted。

JSON Schema能表达结构，Python自定义validator与跨对象语义不会自动在通用JSON Schema验证器里运行。发布SDK时必须保持结构和语义检查一致，不能只导出schema就宣称合同全面受约束。

## 5. 人读模板与权威

模板见 [templates/v0.2/README.md](templates/v0.2/README.md)。用户可以继续给自然语言和已有文档；Ge负责抽取REQ、生成草案与追踪映射，只有实际缺失的方向性决定才交回用户。

| 工件 | 起草 / 生成者 | 权威约定 |
| --- | --- | --- |
| PROJECT / REQUIREMENTS / DECISIONS | 用户材料→Ge | 原始语义来源，修改影响合同需新revision |
| TASK / CONTEXT | Ge | 经确认的JSON与来源引用为当前派发依据 |
| PLAN | 专家 | 冻结plan.json是本轮机器依据 |
| SUMMARY | 设计或投影器 | submission及原件是事实来源；作者不能自审 |
| VERIFICATION | reviewer / 投影器 | 受限调用的decision.json与接纳服务是权威 |
| HANDOFF / STATE | 状态投影器 | ledger+event cursor，不从Markdown恢复作业状态 |

不进行Markdown与JSON的双向自动同步。编辑人读文件会生成待审变更，由Ge显式形成新合同版本；不能直接改变运行中任务。小报告可显式导出项目Git，原件继续通过artifact URI引用。

## 6. 迁移与验收

v0.1保持可读和原有审核归属。要采用v0.2：先登记Project/Component → 固定源baseline → 给旧要求分配稳定REQ并记录来源 → 补可观察行为/关键连接 → 建立coverage → 产生新task revision/hash。旧Review不能自动给新合同放行。

如果前版已经是任务revision=1，新版应取revision=2或新task_id，不能只把schema字符串改成v0.2却覆盖原对象。示例使用同名的独立草案目录只用于结构演示，不是历史任务迁移回执。

本轮验证包括六份新样本/schema、跨对象正例、错误需求/连接/基线/自报pass等反例；接入工具验证两种项目源码不变与路径隔离。具体数量与跳过项见[本轮验证记录](../docs/integration-validation.md)。此前GEMV演示保持原位置与原合同，未假装已被新版服务接管。
